## 一、验收结论

**部分完成，不能整体验收通过。** 结束后执行过程默认折叠、结论/产物移到外层、产物有独立容器，这些改动已存在；但正文、结果摘要和原始事件仍有多个展示来源，最新版本没有彻底解决重复与错位。首字慢是模型请求等待与前端隐藏正文叠加，不能笼统归因于 SSE 或上下文太长。

## 二、已经复现的页面问题

### 1. P0：流式正文被主动隐藏，打字动画没有可靠的展示出口

定位：`client/src/components/ChatPanel.jsx:3654` 附近的 `Message`；重点为 `finalTextBlockIndex`、`isProcessBlock` 和 `visibleBlocks`（3662–3690 附近），及 `assistant-final-answer`（3788 附近）。

当前机制：

1. 最后一个 text 不放进 `foldedProcessBlocks`。
2. `visibleBlocks` 又过滤掉任务运行中的全部 text。
3. 权威最终全文只在 `!streaming` 时渲染。

因此，最新正文 token 即使已进入消息状态，也可能同时缺席过程区与正文区。之前的 text 变成“过程”，最新 text 却不显示；模型有响应与用户看见响应并不是同一个时间点。这是源码直接可确定的问题。本轮没有在首正文 token 到达那一瞬间取得有效截图，不把完成态截图冒充流式证据。

修改方法：不要把 `streaming` 当成“过程文字”的判据。为内容块增加明确语义，如 `kind: narration | answer`，由事件投影维护 `streamingAnswer`；正文区域持续渲染已收到的答案增量。终稿通过稳定 `finalMessageId` 替换/补齐同一条答案，不新增第二份正文。未知旧事件先走兼容适配器，而非直接猜最后一块。

验收：注入 text_delta，尚未发 `agent_end` 时页面已经出现文本；`assistant_final`、`run_finished` 重放后仍只有一份最终答案。动画关闭时直接显示，动画开启时不得拖到整段生成完成之后才开始打字。

### 2. P0：最终答案与完成摘要依然是两套结论

定位：`ChatPanel.jsx:3351`、`:3367`、`:3474`、`:3788`。

0.11.29 的 `conclusionSource` 虽然优先取模型最终答复，但它只影响卡片标题。真正展开的内容 `fullConclusion` 仍取 `completion.summary`，显示条件也仍是 `completion.summary`。页面上方是模型 SSE 解释，展开“结论”则是“任务结束，未检测到文件变更”。历史问候又出现“用户打招呼，无实际任务要求”。折叠只是把第二套答案藏起来，没有统一来源。

截图：[完成态](03-chat-completed.jpg)、[展开的额外结论](04-chat-duplicate-conclusion.jpg)。

修改方法：最终自然语言答案只保留一个展示所有者。结果区域仅显示必要状态与文件入口，不再重复一段答案或通用收尾摘要。`completion.summary` 保留为运行元信息，在没有模型答案的失败/阻塞场景才作为明确标注的兜底。不建议简单把 `fullConclusion` 改成 `conclusionSource`，那会变成同一答案重复两次。

### 3. P1：纯 Chat 的“不要显示结果卡”条件未真正控制渲染

定位：`ChatPanel.jsx:3402`、`:3417`、`:3438`。

`showResultCard` 是 false 也没用：`hasRunDetails` 包含 `completion` 等条件，之后无条件渲染目标达成/文件变更/验证网格。两次无工具 Chat 问答均出现“已完成（推断）/文件变更 0 项/未验收”。

修改方法：分别定义 `showProcess`、`showOutcomeStatus`、`showArtifacts`，不要用“有 completion 数据”代替“需要结果卡”。纯 Chat 成功问答默认只保留答案，确有工具时提供一个过程入口；失败、阻塞、待审批仍要有可行动提示。旧消息缺少 runMode 时，从 Run.task.mode 归一化，避免 `undefined !== 'chat'` 误判。

小细节：嵌入的 `<details>` 在 `ChatPanel.jsx:3439` 被强制 `open={embedded || summaryOpen}`，但没有 `<summary>`，浏览器生成默认“详情”。截图和 AX 均能看到这个非设计入口。嵌入布局用普通 section；需要折叠时提供明确 summary 与可控状态。

### 4. P1：最终回答为何落进过程——仍靠“最后一段”猜测

定位：`ChatPanel.jsx:3662`–`:3680`。

计算了匹配权威答案的 `finalTextBlockIndex`，之后没有使用；实际仍用 `lastTextBlockIndex` 排除一段。追加收尾提示、续写、恢复或多轮助手文本时，较早的回答会被作为过程折叠。历史 10/05 问候可见：过程内有一段自然语言回答，过程外另有收尾回答。[页面证据](07-double-process.jpg)。两段不是逐字重复，但对用户承担了重复回答的作用。

修改方法：用消息/工具调用关联 ID 和明确的 answer/narration 语义分类。保留收尾续写为内部控制事件；不把它制造的新助手消息当成第二个独立回答。旧数据适配要通过固定真实样本测试，不要仅做文本相等判断。

### 5. P1：过程里还有一套嵌套事件列表，不是真正单一时间线

定位：`ChatPanel.jsx:3808`–`:3826`、`:4343`、`:4392`；`client/src/事件展示.js:33` 附近。

先渲染全部 thinking/tool/text blocks，再附加整个 `ExecutionFlow`。后者只在自身列表里合并 tool_start/tool_end，不与前面的 ToolCard 合并。历史问候同时有 complete_task 工具卡和 SSE 内 complete_task 完成行；展开轨迹还能看到 `run_started`、`prompt`、`runtime_health`、`message_start`、`message_end`、`stats` 等原始事件名。时间线并未与前面的过程内容统一排序。

修改方法：统一构建 `processItems`，按服务端序号排序；工具按 toolCallId 更新同一项，不再分别显示卡片和完成事件。主过程采用用户可理解的白名单，原始事件仅放诊断视图；未登记事件不应默认把英文名展示给普通用户。主页面一个折叠入口即可，不再“执行过程 → SSE 事件轨迹 → 工具明细”层层套娃。

### 6. P1：产物数量和列表使用不同集合

定位：`ChatPanel.jsx:3491`–`:3505`。

列表合并交付物与文件变更并按路径去重，但“共 N 项”仍直接把两边长度相加。已有 15 文件历史任务显示“交付 15 / 文件改动 15 / 共 30 项”。[页面证据](06-artifact-count.jpg)。同一份文件可以既是改动又是交付，但不能算成两份文件。

修改方法：先创建一次 `uniqueProducts`，列表、数量、截断提示都消费它。计数标签明确“15 个文件，其中 15 个交付物”。删除/重命名不是普通可打开产物：删除提供 diff/恢复入口；重命名保留 from→to；主要交付物与其他修改分组，内部文件默认隐藏。“全部”应打开指定 runId 的右栏，不能含糊要求展开一个未明确存在的下方清单。

## 三、首字延迟实测与归因

测试模型：MiniMax-M3，快速/low，Chat，无附件、无工具。两条问答不是同样长度；以下仅为样本，不代表平均值或 P95。

| 指标 | 第一次约 200 字问答 | 第二次约 400 字问答 |
| --- | ---: | ---: |
| admission 准备 | 约 0.49 秒 | 约 0.48 秒 |
| model_request_started → 首思考事件 | 8.68 秒 | 4.64 秒 |
| model_request_started → 首正文 token | 10.62 秒 | 7.33 秒 |
| 首正文 token → 权威终稿 | 约 4.12 秒 | 约 5.43 秒 |
| 输入上下文（含缓存读） | 约 5.5k tokens | 约 6.1k tokens |

样本 Run：`run_6f1c9e59-3abe-4967-8fbf-14a01b6d3ffe`、`run_cbe04df0-aba7-4d82-81a2-a53b08ad8a22`。第二条首 token 的服务端发送和本地探针接收时间几乎一致；首事件前存在主要等待，不能把 7 秒全部算成 SSE 传输延迟。`model_request_started` 在 Pi SDK runPrompt 之前发出，所以这段包含 SDK 准备、网络、网关与模型服务，尚未独立测得提供商纯推理耗时。

这两个样本不能支持“默认上下文太长才慢”的结论；历史长会话仍需额外测量 system/tools/history 各项规模。也不能直接承诺换渲染就把真实模型首字降到 1 秒。

### 延迟路径定位与修改

1. **客户端握手门槛**：`ChatPanel.jsx:2438`–`:2445`，发送前等待 streamReady 最多 3 秒。只在未 ready 时生效，本轮热连接样本不是固定等 3 秒。改成按已建立连接快速发送；新连接通过 prompt 返回 runId + 游标回放保证不丢事件，增加握手独立埋点。
2. **Work 的同步准备**：`server/index.mjs:3710` 做一次目录快照；`beginRun`（`server/runs.mjs:429`）又扫描/哈希并复制 before 文件。`runs.mjs:117`、`:123` 最多扫描默认 3000 文件、哈希预算 120MB、复制预算 80MB。外置盘可能放大耗时，但本轮只测 Chat，未量化这条 Work 路径。先补耗时指标，再使用合并快照或增量索引；写操作前 lazy backup/copy-on-write 必须保留回滚安全，不能简单删掉快照。
3. **同步事件落盘**：`server/runs.mjs:545` 每个结构事件 saveRun 整份 JSON，再追加事件；`saveRun` 位于 223 附近。改为内存投影 + 顺序追加日志 + 批量/异步快照，终态持久化设置明确 flush 边界。不要为追求首字丢失恢复能力。
4. **模型与展示预算分开**：首思考、首正文、首可见文字分别计时。真正 token 到前端后立即显示，不再等待终稿；预备状态只告知“已接收/准备中/等待模型”，不得假装模型已经开始生成。
5. **全链路埋点**：client_submit、server_received、admission_ready、sdk_request_dispatched、first_provider_event、first_text_delta、first_dom_text、assistant_final、run_finished。携带 runId、requestId、attemptId、模型、thinkingLevel、上下文分项；统计 P50/P95，而不是一条“总耗时”。

建议预算：输入反馈 <100ms；token 接收到 DOM 可见 P95 <100ms；简单热 Chat 的服务端准备 P95 <500ms（需正式压测验证）；真实模型 TTFT 单独展示与比较。打字动画允许关闭/调速，但追赶缓存不能累积到秒级。

## 四、“模型连接异常”定位

### 确定的前端生命周期问题

`ChatPanel.jsx:1906` 附近每次 agent_retry 都设置 retrying，并向主消息流追加“模型连接异常”。`:1934` 附近只处理 agent_retry_end.success=true，失败不清理。`agent_error`（2046）和 `run_finished`（2118）也没有统一清理 connectionNotice。结果是最后失败后仍可能保留“正在重试”状态。

修改：独立 `ConnectionState` 与 `RunState`。retrying 只在当前 attempt 活跃时存在；recovered/failed/cancelled 终态统一清除定时器和重试状态。网络错误、鉴权/配额、供应商未配置、运行时依赖故障、主动取消分别显示可行动文案。重试明细进入过程，不给每次 attempt 新增永久系统消息。连接提示不能反过来改变已经完成的 Run 状态。

### 后端确有不同类别故障，不能都叫网络

本轮查看的当日服务/运行记录包含：

- commandcode/deepseek 路径的 `Connection error.`，实际网络类失败，需供应商端 requestId 与网关记录才能继续确认根因。
- `opencode/deepseek-v4.1-flash` 的 `Provider is not configured: opencode`，属于供应商配置问题，不应提示检查网络/反复重试。
- 13:32 MiniMax 的旧嵌套 Pi AI `anthropic-messages.js` 路径找不到。当前顶层模块存在，22:08 重启后本轮两次 MiniMax 均成功。结合依赖布局与时间，旧进程在依赖更新后仍持有旧 lazy-import 路径是合理推断，尚不是彻底证明。

定位：`server/agent.mjs:453` 的 classifyAgentError；`:2481` 的 auto_retry_start 转发没有把完整分类契约交给客户端；`:318` 的 settled replay 退避为 1.5/5/12 秒，还有 SDK 重试与其他恢复层。当前首事件超时 45 秒、空闲超时 120 秒（369/372 附近），不是固定 4–5 秒。

修改：标准错误结构 `{category, code, retryable, attemptId, provider, requestId, userAction}`；单一全局重试预算协调 SDK/应用重放/备用模型，禁止非重试错误进入多层重试。升级依赖后由监督器进行受控服务替换与健康检查，不能在旧进程仍运行时让原路径消失。

## 五、产物与滚动的其他风险

- `工作产物面板.jsx:134` 先排除无 artifacts 的 Run，再在 166 附近从剩余 Run 取 latestRun。最新一轮无产物时，改动区可能拿到较旧一轮；`artifactScope==='run'` 且 selectedRunId 为空时也退回全会话。应先确定唯一目标 Run，再投影其变化；不能因为无交付物就排除它。会话范围标签也应改为“会话产物”，不总叫“本轮产物”。此项为源码风险，未专项 UI 复现。
- `工作产物面板.jsx:155` 直接 flatMap run.artifacts，仅排除 deleted。主清单应消费 role 归一化后的交付物集合，并对同路径多版本说明归属；不要把每一次修改都无差别叫成果。
- `server/runs.mjs:411` 的 filterRunChanges 在 touchedPaths 为空时保留所有非噪声差异。并发共享工作区可能误归属；需增加并发两个 Run 的测试，并把无追踪差异标为未归属线索，不自动宣告交付。
- `ChatPanel.jsx:3794` 的 open={isTaskLive || processOpen} 会让运行中折叠不能持久；`styles.css:10012` 附近 live-plain 强制 max-height:none/overflow:visible，因此不是有界内部滚动。自动跟随要对真正滚动容器生效，用户向上阅读时停止跟随，并提供“回到最新”。
- `styles.css:1394` 用 flex order 把过程移到答案上方，JSX 顺序却相反。应以 DOM 明确表达过程/答案/文件顺序，避免视觉与键盘阅读顺序不同；不要继续追加 CSS 顺序覆盖。
- 待审批/待用户回答不能随着历史过程一起隐身。应有独立持久的行动区；此项纳入专项测试，本轮未创建真实审批。

## 六、推荐的统一展示结构

```text
一次用户请求 / runId
├─ 一个过程区域：思考、进度说明、工具、重试（同序号流，结束默认收起）
├─ 一个最终答案：流式可见，终稿原位补齐，不重复生成结论卡
├─ 必要的行动提示：询问、审批、失败、未完成
└─ 一个文件区域：主要交付物 + 其他改动；数量来自同一去重集合
```

通用完成摘要、经验记忆、原始 SSE 日志不再占主对话。经验建议放设置/记忆审核；原始事件放诊断入口。成功 Chat 默认只显示答复；Work 成功显示答复与真正文件；失败明确失败并保留已有文件，不假称全部完成。

后端/投影字段建议：`runId/seq/eventId/messageId/toolCallId/attemptId`、`phase`、`contentKind`、`answerVersion`、`lifecycle`、`outcome`、`artifactRole`。生命周期与目标完成程度保持分离。终态收束和折叠属于展示规则，不属于“再调用一次模型总结”的理由。

## 七、实施顺序与验收条件

1. **先修正文与结论单一来源（P0）**：Message 分类/流式出口、finalMessageId 幂等、RunSummary 移除重复文本。采用真实历史样本和录制 SSE 测试，不能仅测纯投影。
2. **再修卡片与产物（P1）**：Chat 无空卡、uniqueProducts 同源计数、删除/重命名入口、指定 runId 不退回旧结果。
3. **合并过程视图（P1）**：同一 toolCallId 一项、保留准确时间顺序、仅一个过程折叠层、原始事件移到诊断。
4. **修错误状态（P1）**：错误分类与重试预算；终态不遗留 retrying；取消不叫网络故障；配置错误不给用户反复等待。
5. **做耗时优化（P1/P2）**：先补全链路计时，再测 Work 外置盘大目录、冷启动与长上下文；据指标改快照和落盘。不要用前端动效遮盖真正等待。

必须补的端到端用例：

- 首 text_delta 到达且运行未结束，文本可见；首字→DOM 延迟可测。
- 一次 tool_start、多个 tool_update、tool_end 只显示一项，进度说明与对应调用正确排序。
- 收尾续写/恢复/assistant_final/run_finished 重放后只有一份答案，不进入过程重复回答。
- Chat 无文件/工具没有目标达成空卡；Work 有文件仍保留直接打开和 diff。
- 同 15 文件分别出现在 changes/deliverables：唯一数量 15；显示 6 项后“查看全部”有明确入口。
