# 工作流事件流与对话流整理 · 任务编排优化建议（2026-09-22）

> 数据窗口：事件流全量（12,622 条 / 12.1MB / 637 个 Run）与最近 30 天 Run 记录（505 个）。
> 复现：`node scripts/任务复盘.mjs 30`；本文的事件/编排数字均来自 `.oaw/events/事件流.jsonl` 与 `.oaw/runs/*.json`。

## 0. 结论速览

1. **完成语义几乎缺失**：30 天里只有 **4%（21/505）** 的 Run 显式调用 `complete_task`，其余靠框架推断——"任务真的做完了吗"目前基本没有可靠答案。
2. **验收环节基本空缺**：`verificationStatus` 未检查 446/505（88%），有校验记录的只有 59 个（12%）。
3. **计划覆盖率低、且容易漂移**：只有 12% 的 Run 建了 todo，其中 **40%（24/60）** 收尾时待办没做完；同时有 74 个 Run "工具调用 ≥5 次但没有任何计划"。
4. **事件流有结构性冗余与不一致**：`write_started`/`write_locked` 成对出现占总事件 **21.6%**；协议里声明的 19 种"生命周期事件"（turn/message/审批/模型回退/ steer 等）**并未持久化**，而 9 种已持久化的事件又不在生命周期保护集合里。
5. **轮次预算缺失**：长任务出现 46–68 轮模型回合（review 排查一次 68 轮 / 113 次工具），中途没有"先阶段汇报再继续"的强制点。

## 1. 事件流现状

### 1.1 协议分层（Event Protocol V2）

代码位置：`server/事件协议.mjs`、`server/事件存储.mjs`、`server/运行轨迹.mjs`。

| 层 | 内容 | 是否持久化 | 淘汰策略 |
| --- | --- | --- | --- |
| 生命周期事件（`LIFECYCLE_EVENT_TYPES`，41 种） | 运行/回合/消息边界、工具边界、写入与产物、审批、重试与回退、错误、完成 | 部分（见 1.3-A） | 通道历史窗口（4000）内**不允许被增量挤出** |
| 增量事件（`DELTA_EVENT_TYPES`，3 种：token / thinking / tool_output） | 仅实时渲染 | 否 | 优先淘汰 |
| 其它（内存/磁盘保留） | run_started / prompt / memory_* / step_updated 等 | 是 | 普通 FIFO |

前后端约定：`streamId` 代际 + `resolveReplayCursor` 断线回放 + `isHistoryTruncated → stream_resync`；前端 `client/src/运行轨迹.js` 用事件 key 做幂等归约（同一份归约器同时服务实时流与历史回放）。

### 1.2 数据体检（全量 12,622 条 / 12.1MB / 637 Run，平均 20 条/ Run）

| 事件 | 条数 | 占比 | 体量 | 备注 |
| --- | --- | --- | --- | --- |
| tool_start | 2,784 | 22.1% | 2.1MB | 与 tool_end 1:1 |
| tool_end | 2,697 | 21.4% | 5.9MB | 结果体量最大的来源（含 CLI 全文） |
| write_started | 1,357 | 10.8% | 0.86MB | 与 write_locked 恒成对 |
| write_locked | 1,357 | 10.8% | 0.57MB | **可合并** |
| run_started | 629 | 5.0% | 0.65MB | 比 run_finished 多 58 条 |
| run_finished | 571 | 4.5% | 0.19MB | — |
| agent_retry | 345 | 2.7% | — | 通道不稳定仍偏多 |
| agent_error | 274 | 2.2% | — | 失败面 |
| write_cleaned | 235 | 1.9% | — | 丢弃 staging 的次数（失败/取消） |
| agent_summary | 56 | 0.4% | 0.32MB | 总结体量大 |
| 其余 11 种 | 219 | 1.7% | — | — |

关键观察：

- 增量事件持久化 **0 条**（符合设计：token/thinking/tool_output 只走实时 SSE）。
- 生命周期/非生命周期比例：11,394 / 1,228 → 事件流没有失控，但**写入类事件占比过高**（write_* 共 21.6% + 工具边界 43.5%）。
- 事件最多的 Run：389 条 / 14.5 分钟（tool_start×100 + write_started×87）——事件量几乎与工具调用次数线性相关。

### 1.3 问题清单（可验证）

**A. 协议声明与持久化清单不一致（单一来源缺失）**

- 在 `LIFECYCLE_EVENT_TYPES` 里、但**不落盘**：`run_admitting / run_admitted / thinking_level / agent_started / turn_started / turn_ended / message_start / message_end / tool_approval_request / tool_approval_resolved / agent_model_fallback / agent_model_fallback_failed / context_compacting / context_compact_warning / agent_turn_end / agent_queued / agent_queue_update / steer / stats`（19 种）。
- 落盘、但**不在生命周期保护集合**：`run_started / run_recovered / run_cancel_requested / run_recovery_started / prompt / step_updated / artifact_published / memory_*`（9 种）。
- 后果：重连回放时，回合边界、审批、模型回退、排队与 steer 在历史里**不可重建**；而 run_started 这类"必须保留"的事件在高频流量下可能被挤出窗口。

**B. 写入事件冗余**：`write_started` + `write_locked` 恒成对（代码里连续 emit），占总事件 21.6%，其中 `write_locked` 不携带额外信息。

**C. 终态不闭环**：`run_started` 629 条 vs `run_finished` 571 条，58 个 Run 只有开始没有收尾（取消/恢复路径缺终态）；`run_recovered` 77 条说明服务重启频繁打断。

**D. 无归档/轮转**：单个 `事件流.jsonl` 已经 12.1MB 且持续增长，读取路径是"整文件加载进内存（上限 20000 条）"（`事件存储.mjs`），长期会变慢。

**E. 新增事件未纳入持久化**：本轮新增的 `tool_repeat_warning` 已写入 Run 事件，但不在 `PERSISTED_TYPES` 里，根级事件流看不到（复盘会漏）。

## 2. 对话流现状

### 2.1 一轮对话的生命周期（服务端 → SSE → 前端）

```
用户消息
 → /api/agent/prompt（建档 Run、能力计划）
 → run_admitting / run_admitted → capability_plan / mode_policy / thinking_level
 → agent_started → turn_started
   → model_request_started → message_start → (thinking/token 流) → message_end
   → tool_start → (tool_output 流) → tool_end            ← 可多轮
   → write_started/write_locked → artifact_staged
 → todo_updated / 中途 ask_user / 审批(request→resolved)
 → agent_turn_end → assistant_final → agent_summary
 → 发布产物 artifact_materialized → run_finished（携带 completion / verificationStatus）
```

前端 `ChatPanel.handleEvent`（约 1,500 行）按 `runId` 锚定当前 Run、丢弃旧 Run 事件；执行事件进入 `enqueueExecutionEvent` 队列，再由 `client/src/运行轨迹.js` 归约为可渲染轨迹：

| 归约产物 | 来源事件 | UI 呈现 |
| --- | --- | --- |
| `tools[]`（按 toolCallId 聚合） | tool_start / tool_output / tool_end | 折叠的"本轮工具"清单（含耗时、失败标记） |
| `files[]` | file_changed | 本轮文件变更 |
| `errors[]` | agent_error / officecli_failed | 错误条 |
| `completion` | task_completed → run_finished.completion → 推断 | 完成徽标（已完成/部分完成/受阻/失败/取消） |
| `phase` | run_admitting → tool_start → agent_end → run_finished | 准备 → 执行 → 整理产物 → 完成/失败 |

折叠态摘要 `runTraceSummaryText`：`已调用 N 个工具 · x 成功 · y 失败 · z 执行中 · M 个文件变更 · K 次错误 · 完成状态`。

### 2.2 问题清单

1. **摘要缺两个关键项**：没有"计划进度（待办 x/y）"和"验收结果（passed/failed）"——而这两项正是判断"任务是否真的完成"的依据（见 3.1）。
2. **事件分支过散**：`ChatPanel` 直接处理 80+ 种事件类型（其中 review_* 10 种、模型通道类 6 种、写入类 8 种），归约器只覆盖了其中 14 种；新增事件容易"只在一个地方处理"。
3. **完成语义展示弱**：推断出的完成（`source:"inferred"`）与显式 `complete_task` 在 UI 上区分度不足，用户难以发现"这轮其实没有验收"。
4. **阶段（phase）粒度粗**：只有 准备/执行/整理/完成 四段，缺少"计划 → 执行 → 验证 → 交付"的关键节点，长任务看不出当前处于哪一步。

## 4. 优化建议

### P0 —— 让"完成"可判定（改动小、收益最大）

1. **收尾强制完成声明**：Run 进入收尾（`agent_end` 且无工具在跑）时若没有 `complete_task`，由运行时注入一次提醒（`steer` 或补一轮短提示）："请用 complete_task 声明 success/partial/blocked/failed 与未完成项"。目标：显式完成率从 4% 提到 70%+。
2. **验收前置到产物发布**：`publishStagedRun` 前对 Office/文档类产物自动跑一次 `validateArtifactFile`（已有）+ 关键文件回读哈希，结果写入 `run.validations`；UI 在产物卡上显示"已验收/未验收/验收失败"。
3. **摘要补齐两项**：`runTraceSummaryText` 增加 `待办 x/y` 与 `验收 passed|failed|未检查`；默认折叠态就能看出这轮是否闭环。

### P1 —— 计划与轮次纪律

4. **按复杂度触发计划**：当满足任一条件（预计产物 >0 / 工具预算 ≥5 / 多文件 / 收到"帮我整理/审查/生成"类指令）时，运行时在 prompt 里显式要求先 `todo` 再动手；否则允许直接回答（避免短问答也建计划）。
5. **计划漂移收口**：收尾时若存在未完成待办，要求把缺口写进 `complete_task.incomplete/blockers`；`运行轨迹` 把"未完成待办"计入摘要（当前只统计工具与文件）。
6. **轮次预算与阶段汇报**：给长任务加软预算（例如 25 轮）：超过后先产出一段阶段结论 + 用 `ask_user` 询问是否继续；对浏览器搜索类任务限制轮数（现有一段 68 轮的先例）。
7. **重复调用抑制复测**：P2 的 `tool_repeat_warning`（第 3 次重复 steer 提醒）上线后，用 `node scripts/任务复盘.mjs 7` 复测"同参数重复 ≥3 次的 Run"占比，目标从 4% 降到 2% 以下。

### P2 —— 事件流与对话流的结构性整理

8. **模型/存储单一来源**：把 `LIFECYCLE_EVENT_TYPES`（协议）与 `PERSISTED_TYPES`（存储）合并成一张 `EVENT_REGISTRY`（字段：type、lifecycle、persist、payload 上限），两处都从它派生，消除 19 种事件"声明了但没落盘"与 9 种事件"落盘但不受保护"的错位；顺手补 `tool_repeat_warning`。
9. **去掉写入冗余事件**：合并 `write_started` + `write_locked` 为一个事件（`write_started` 携带 `locked:true`），或把 `write_locked` 降级为 delta；可让事件流体积/条数下降约 11%。
10. **终态闭环**：取消/失败/恢复三条路径都补 `run_finished`（或统一发 `run_ended`），保证 `run_started` 与终态 1:1；把 `run_recovered` 计数纳入健康面板。
11. **事件流归档**：`事件流.jsonl` 按月/按大小轮转（如 8MB 切一个 `事件流-<yyyymm>.jsonl`），并写一份轻量索引（seq 区间 → 文件），读取仍按尾部窗口；避免 20k 条上限被历史噪音占满。
12. **对话流阶段化**：把 `phase` 从 4 段扩到 5 段（计划 → 执行 → 验证 → 交付 → 完成），由 `capability_plan/todo_updated`、工具边界、`validations`、`artifact_materialized`、`run_finished` 驱动；前端执行流按阶段分组渲染（现在按时间平铺）。
13. **归约器收口**：把 `ChatPanel.handleEvent` 里"事件 → 状态"的映射继续下沉到 `运行轨迹.js`（或新的 `事件归约.js`），ChatPanel 只做渲染订阅；新增事件先在归约器登记，避免"80+ 分支散落"。

### 建议的落地顺序

1. P0-1（收尾强制完成声明）→ 2. P0-3（摘要补齐）→ 3. P0-2（产物验收前置）→ 4. P2-8（事件注册表）→ 5. P1-4/5（计划与漂移）→ 6. P1-6（轮次预算）→ 其余。

每步都可用现有脚本验证：`scripts/任务复盘.mjs`（完成率/计划率/重复率）、`scripts/重复调用抑制测试.mjs`、`npm run verify`，以及 `docs/任务编排与工具调用复盘-20260921.md` 里已建立的基线条。
