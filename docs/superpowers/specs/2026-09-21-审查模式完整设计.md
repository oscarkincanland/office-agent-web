# Open Plan Review 审查模式完整设计

## 1. 目标与边界

### 1.1 目标

在现有 `Chat` 与 `Work` 之外增加英文标识为 `Review` 的审查模式，形成一条可追溯、可恢复、默认不破坏原文的文档审查闭环：

1. 根据当前打开文件、`@` 文件或附件判断材料类型与审查范围。
2. 先检索规范库，再对真正读过全文的规范文件建立证据台账。
3. 按规范要求读取并分析材料，生成审查报告和批注稿/审查副本。
4. 原文件在用户明确确认前不可被修改；确认后才允许写回原文件。
5. SSE 事件流与结论文件都明确显示“搜索过什么、实际读过什么、实际采用什么”。
6. 事件、任务、产物和证据台账都进入 Run 持久化，恢复会话后仍保持每轮边界。

### 1.2 非目标

- 不把 Review 变成新的通用 Agent；Review 不默认开放 Bash、地图编辑、浏览器自动化或长期记忆写入。
- 不把知识库搜索命中直接当成规范依据；只有 `kb_read` 成功读取全文后才算“已读取”。
- 不自动覆盖原文，不绕过已有工具审批、工作区写入锁和文件权限限制。
- 不在本阶段重写 Pi SDK、SSE 传输层或文档预览引擎；仅接入已有能力并补齐状态与证据。

## 2. 三种模式定义

| 模式 | 英文标识 | 权限边界 | 典型结果 |
| --- | --- | --- | --- |
| Chat | `Chat` | 只读检索、解释、引用；不修改文件 | 回答、资料摘要、引用列表 |
| Work | `Work` | 完整任务工具链，按现有审批与工作区规则执行 | 修改文件、分析结果、工作产物 |
| 审查 | `Review` | 读取材料与规范，生成报告/副本；原文写回必须在确认后 | 审查报告、批注稿副本、规范依据台账 |

历史 `office` 模式继续归一化为 `Work`，不再向用户暴露旧名称。

## 3. Review 工作流

### 阶段 A：材料识别

1. 读取当前工作文件、结构化引用和附件清单。
2. 判断材料类型：规划文本、研究报告、会议纪要、表格、汇报材料、合同/制度或其他。
3. 若材料不足以判断，调用 `ask_user` 只询问一个阻塞问题。
4. 通过 `todo` 建立 4—6 项审查待办，任务栏显示这些待办，而不是把每个工具调用当作待办。

### 阶段 B：规范发现与读取

1. 调用 `kb_search` 查找可能适用的通用规范、模板、条文和项目约束。
2. 搜索结果以“候选规范”事件显示，状态为 `candidate`，不能直接作为结论依据。
3. 对真正用于判断的候选项调用 `kb_read`。
4. `kb_read` 成功后分配稳定编号 `R-01`、`R-02`……并记录：编号、标题、相对路径、知识库根、读取时间、内容摘要哈希、用途状态。
5. 每条审查结论必须引用一个或多个 `R-*`；未实际读取的搜索候选只能标记为“未采用”。

### 阶段 C：材料审查

1. 用 `officecli` 读取 Word/Excel/PPT 的结构和正文；纯文本使用 `read`。
2. 按材料类型和已读取规范逐项检查：结构完整性、事实与数据、格式/体例、逻辑一致性、风险与缺项。
3. 每条问题使用稳定编号 `F-01`、`F-02`……并包含：位置、问题、严重程度、依据 `R-*`、建议。
4. 读取规范但未用于具体判断的文件仍列入依据台账，状态为 `read-not-applied`，避免把“读过”误写成“采用”。

### 阶段 D：生成安全副本

默认在当前工作区生成：

- `审查报告_<原文件名>.md`：结论、问题清单、依据台账、未采用候选规范、假设和下一步。
- `批注稿_<原文件名>.<原扩展名>`：原文件的副本；批注只写入副本。
- 若格式暂不支持副本批注，则生成 `批注建议_<原文件名>.md`，不得声称已修改 Office 原文件。

报告末尾必须包含“规范依据台账”：

| 编号 | 标题 | 路径/根目录 | 实际读取 | 本轮采用 | 支持的问题 |
| --- | --- | --- | --- | --- | --- |
| R-01 | … | … | 是 | 是 | F-01、F-03 |

### 阶段 E：用户确认与原文写回

1. 报告和副本验证成功后，Review 调用 `ask_user`，明确询问：“是否将已确认的批注/修改写回原文件？”。
2. 等待期间 Run 为 `waiting_user`，事件流显示“等待审查写回确认”。
3. 用户确认后，运行时将 `reviewConfirmed=true`，并发出 `review_confirmed`；仅此之后才允许针对受保护原文件执行 `officecli add/set/batch/...` 或 `write/edit`。
4. 用户拒绝或超时，保留报告和副本，原文不变，Run 以 `partial` 或 `blocked` 收尾。
5. 原文写回后必须回读验证，报告追加“写回结果”和验证信息。

## 4. 事件协议与持久化

### 4.1 新增事件

| 事件 | 触发条件 | 关键数据 |
| --- | --- | --- |
| `review_material_classified` | 材料识别完成 | `materialType`, `confidence`, `targets` |
| `review_source_search_started` | 开始查规范 | `query` |
| `review_source_search_result` | 返回候选规范 | `query`, `candidates[]` |
| `review_source_read_started` | 开始读取某规范 | `sourceId`, `path`, `root` |
| `review_source_read` | 全文读取成功 | `sourceId`, `title`, `path`, `root`, `contentHash`, `status=read` |
| `review_source_applied` | 规范被具体问题/结论采用 | `sourceId`, `findingIds[]`, `reason` |
| `review_source_unused` | 读取过但未采用 | `sourceId`, `reason` |
| `review_waiting_confirmation` | 副本产物完成，等待写回确认 | `sourceFiles[]`, `copyFiles[]`, `reportFiles[]` |
| `review_confirmed` | 用户明确确认写回 | `answer`, `runId` |
| `review_write_blocked` | 确认前触碰原文 | `path`, `kind`, `reason` |

上述事件通过当前 SSE 通道实时发送，并由 `recordRunEvent` 写入 Run；恢复会话时从 `run.events` 回放，不依赖当前页面是否一直在线。

### 4.2 证据台账数据结构

```js
{
  sourceId: "R-01",
  title: "……",
  relPath: "…….md",
  rootName: "……",
  contentHash: "sha256:……",
  readAt: "2026-09-21T……Z",
  status: "read | read-not-applied | applied | candidate | failed",
  findingIds: ["F-01"],
  reason: "用于判断章节结构和报批材料要件"
}
```

## 5. 权限与安全

- Review 的工具白名单：`read`、`grep`、`find`、`ls`、`ask_user`、`kb_search`、`kb_read`、`context_read`、`skills_search`、`skills_read`、`officecli`、`write`、`edit`、`todo`、`complete_task`。
- Review 禁止 `bash`、地图写入、浏览器自动化和 `memory_update`。
- `write/edit/officecli` 在 `reviewConfirmed=false` 时只允许生成副本/报告；若目标解析为当前材料或引用的原文件，必须抛出 `REVIEW_CONFIRMATION_REQUIRED` 并记录 `review_write_blocked`。
- 现有工具审批、工作区写入锁、Access denied/EPERM/EACCES 诊断和产物验证继续生效。
- 规范文件只读；报告和副本必须写入当前工作区。

## 6. 前端交互

1. 顶部模式切换增加 `Review`，显示盾牌/审查图标和 tooltip：“先依据规范生成报告与批注副本，确认后才写回原文”。
2. Review 模式下显示安全提示：`原文保护中 · 先生成副本`。
3. 执行过程继续默认折叠，但 Review 事件始终进入 SSE 事件流；展开后可看到候选规范、实际读取、采用依据和写回保护。
4. 本轮总结增加“规范依据（已读取 N / 采用 M）”区域，列出 `R-*`、路径、状态和对应问题；每轮恢复仍单独展示。
5. “本轮工具”继续默认折叠；规范依据不混入工具列表，避免阅读时被大量工具输出冲掉。
6. 报告/副本产物沿用现有自动打开文档预览逻辑；点击 `R-*` 先显示路径和状态，若来源在可访问文件根内则打开预览，否则显示只读来源信息。

## 7. 失败与恢复

- `kb_search` 无命中：显示“未找到候选规范”，允许用户继续按通用审查或补充知识库引用，但报告必须写明。
- `kb_read` 失败：记录 `failed`，不得把该规范列入已读取依据；必要时询问用户是否继续。
- Office 读取成功、写入失败：报告仍可完成，批注稿标记为未生成或未写入；原文不受影响。
- SSE 断线：Run 事件与证据台账从磁盘恢复，前端使用事件游标回放；不能重复生成第二份结论。
- 服务重启：活动 Run 标记为 `recovering`，用户选择继续/重试；继续时复用同一 `runId` 的事件与证据台账，不重置 `R-*` 编号。

## 8. 验证标准

### 单元/静态验证

- `TASK_MODES` 包含 `review`；`normalizeTaskMode`、模式标签、工具策略和能力计划均可处理 Review。
- 前端模式切换、历史恢复、事件标签和总结模式标签均显示 Review。
- `kb_search` 只产生候选事件；`kb_read` 才产生已读取事件，并带稳定 `R-*` 和哈希。
- Review 确认前对原文件的写入被拒绝，且有 `review_write_blocked`；对报告/副本的写入允许。
- 新事件进入 Run 持久化，并可在历史恢复后显示。

### 集成验证

1. 以一个 docx 或 xlsx 为当前文件启动 Review。
2. 检查事件顺序：材料识别 → 搜索候选 → 读取规范 → 审查 → 报告/副本 → 等待确认。
3. 检查报告确实列出实际读取的规范文件、采用状态和问题引用。
4. 在未确认时尝试写回原文，确认得到 `REVIEW_CONFIRMATION_REQUIRED`。
5. 点击确认后写回副本/原文，回读验证并检查恢复会话仍只有一份本轮总结。
6. 运行 `npm.cmd run verify`、前端构建和现有 SSE/产物/Office 回归测试。
