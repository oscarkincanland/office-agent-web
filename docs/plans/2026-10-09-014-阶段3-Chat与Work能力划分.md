## 目标（D1）

> Chat 模式只是作为查询的功能，能读取和分析总结；具体操作（增加新图层等）还得 Work 模式来操作。

阶段 0 已落地**工具白名单**（`READ_ONLY_TOOLS` 加三个只读地图工具）。本阶段解决**产品一致性**：

1. **能力计划与实际权限一致**——现状 `capability_plan` 标注 `map: enabled`（`task.mjs:106,116`）而 Chat 模式下没有任何 map 工具，这种"说得到做不到"是 X1 的根因，必须从机制上杜绝。
2. **拒绝要可解释**——Chat 模式下用户要求写操作时，给出明确引导而不是沉默。
3. **两端能力说明可见**——用户知道 Chat 能做什么、Work 能做什么。

## 改动点

### 3.1 `capability_plan` 按模式标注地图能力

**位置**：`server/task.mjs:106`

```js
// 现状：无论什么模式都是 "planned"
if (map) capabilities.push({ id: "map", label: "地图工具", status: "planned", required: false, reason: "本轮出现地图、图层或空间分析意图" });
```

**改为**按模式区分 `status` 与 `reason`：

| 模式 | status | reason（示例） |
| --- | --- | --- |
| Chat | `ready` | "只读地图查询与分析（不落盘）" |
| Work | `ready` | "地图查询、分析与图层写入" |
| Review | `not_applicable` | 不涉及 |
| Office | `not_applicable` | 不涉及 |

**同时**：`routing.map`（`:116`）的值从 `"enabled"` 细化为 `"read_only"`（Chat）/ `"read_write"`（Work）/ `"not_needed"`。

**一致性校验（新增测试断言）**：`planTaskCapabilities` 的 `capabilities` 里出现 `id: "map"` 时，`toolPolicyForMode(mode).tools` 必须至少含一个 `map_*` 工具。**这条断言是防止 X1 复发的机制保障**，建议写入 `scripts/主任务流可信度测试.mjs`。

### 3.2 Chat 模式下的写操作拒绝（可解释）

**现状**：Chat 模式没有写工具，模型只能回答"受只读模式限制"（实测 `run_c897ebce`）。

**改为**：在系统提示（Pi prompt）里按模式注入**能力边界说明**，让模型在 Chat 模式下**主动引导用户切模式**，而不是让用户困惑。

**位置**：`server/task.mjs:164`（现有 `task.mapProject ? "当前地图项目：..." : ""` 附近），扩展为地图能力说明段：

```
当前地图能力（Chat 模式）：可查询数据集与图层、生成临时可视化、清除临时结果。
不可执行：新增/修改/删除图层、保存分析结果——这些需要用户切换到 Work 模式。
当用户要求写操作时，明确说明需要切到 Work 模式，不要尝试绕过。
```

Work 模式对应改为"可执行全部地图操作（写操作需审批）"。

### 3.3 前端：模式能力提示

**位置**：`client/src/App.jsx:1505-1545`（模式切换按钮）。

- 复用现有 `title` 属性（已有"Chat：只读问答和资料检索"等），补充地图能力一句。
- 地图模块内（阶段 0.4 新增的模式切换）同步。
- **可选**：Chat 模式下用户在地图里点"保存为图层"时，弹出"需要 Work 模式，是否切换？"（当前该按钮在可视面板，属阶段 2 产出）。

### 3.4 与既有 mcp 审批模型的对齐

**背景**：`审批策略.mjs:20-21` 有"MCP 自身明确标记为只读时由调用端跳过审批"的先例。

**做法**：本阶段把"只读地图工具"也纳入同一语义——`map_read`/`map_analyze`/`map_clear_analysis`/`map_datasets` 标记为**只读工具**，`requireToolApproval` 对它们直接放行（现在它们本来就没有审批调用，属于天然一致，但要显式声明，避免将来加审批时误伤）。
