# 规聚后续稳定性与智能体工程管理改造

## 1. 计划定位

本计划承接《规聚项目稳定性与智能体工程管理实施计划》，只处理当前 Web 项目中尚未完成的工程化内容，不重复改造已经通过验证的事件流、会话切换、任务中心和基础成果闭环。

本轮目标不是继续堆叠功能，而是先让 Agent 的执行过程可控、可恢复、可验收，再完善 Chat、Agent、项目分类、记忆沉淀和 Pi 运行时管理。

## 2. 当前基线

已经具备的能力：

- 项目、工作区、会话和 Run 的基础绑定。
- 多会话后台事件、历史会话、未读状态和任务中心。
- Run 取消、继续、重试、服务重启后的恢复标记。
- Chat、Office、Agent 的基础工具权限策略。
- Skills 预检、文档读取缓存、Office CLI 自动判断。
- Run 快照、基础回滚、产物校验、成果固定和发布记录。
- 记忆建议生成和人工确认写入。
- 服务端语法、前端构建、接口冒烟和已有闭环检查通过。

当前仍存在的主要问题：

- Agent 和 Office 仍可能直接写入项目工作区，没有统一的临时产物、写入锁和原子发布。
- 记忆只有确认写入，没有拒绝、编辑、合并、历史和服务端强制隔离。
- 项目类型可以展示和分组，但没有完整的项目创建、编辑、归档和项目级设置。
- 顶层仍显示 Chat、Office、Agent / 创作三个模式，Office 内置化和 Profile 化尚未收敛。
- 知识库和 Skills 还没有形成真正独立的只读 Chat 体验。
- Pi SDK 仍由业务代码直接调用，没有 Runtime 管理层。
- Office 产物目前主要是结构校验，缺少内容级和视觉级验收。
- 真实并发、重启、模型故障和浏览器端回归测试不足。

## 3. 范围和边界

### 本计划包含

- Agent 执行稳定性和文件成果安全发布。
- 项目分类、项目设置、会话沉淀和记忆治理。
- Chat 与 Agent 的前端结构收敛。
- Office CLI 的内部能力化和成果验收。
- Pi Runtime 管理层的第一版。
- 跨层稳定性测试、版本同步和交付检查。

### 本计划暂不包含

- 桌面端 Electron 改造。
- 团队协作、远程数据库、对象存储和多用户权限系统。
- Pi 内核源码修改。
- 依赖 Pi 内部能力才能实现的 token 级 checkpoint；在 Pi 不支持前，继续使用可解释的 JSONL 重开和恢复提示。

## 4. 最终产品原则

- Chat 负责理解、查找、问答和引用，不负责修改文件、不负责写入记忆。
- Agent 负责执行任务、调用工具、生成成果和提交记忆建议。
- Office CLI 是 Agent 的内部文档执行能力，由任务自动判断是否启用。
- 创作、研究、Office、GIS、数据分析是 Agent Profile，不再作为顶层模式堆叠。
- 项目是所有会话、Run、成果和记忆的归属边界。
- 所有文件成果先进入 Run 的受控区域，验证通过后才能固定到项目成果。
- 所有长期记忆先进入待审核状态，用户确认后才能沉淀。
- 事件流继续沿用现有设计；新增能力必须接入同一条事件审计链。

## 5. 分阶段实施计划

### 阶段一：Agent 执行稳定性底座

目标：解决“多个会话会不会互相覆盖、失败后会不会留下半成品、服务崩溃后状态会不会损坏”三个问题。

实施内容：

1. 建立 Run 受控目录：`.oaw/runs/<runId>/staging/`、临时输入目录和验证结果目录。
2. Agent 生成的新文件默认写入 staging，不直接显示为正式成果。
3. 对已有文件的修改建立文件级锁，记录 Run、会话、持有时间和锁状态。
4. 对同一文件的并发修改返回明确的占用信息，不静默覆盖。
5. 完善取消、异常和超时后的锁释放与临时文件清理。
6. 产物验证通过后，使用原子替换或受控复制发布到项目工作区。
7. 将 `runs.json`、项目配置、产物记录、记忆建议和事件追加写入统一为临时文件加原子替换或安全追加策略。
8. API Key 文件至少增加权限检查和异常保护；在桌面端之外，先保证本地服务不会因普通错误暴露凭据。
9. 在事件流中记录 `write_started`、`write_locked`、`write_rejected`、`artifact_staged`、`artifact_published` 和 `write_cleaned`。

建议涉及文件：

- `server/runs.mjs`
- `server/agent.mjs`
- `server/成果管理.mjs`
- `server/事件存储.mjs`
- 新增 `server/写入协调.mjs`

验收标准：

- 两个会话同时修改同一文件时，一个获得锁，另一个得到结构化冲突错误。
- Agent 在生成中途取消时，不留下可被成果列表误认为正式产出的半成品。
- 服务在持久化过程中异常退出后，重启能够识别损坏记录并保留上一份有效状态。
- 产物只有在验证通过和发布完成后，才显示为正式成果。
- 原有 `npm.cmd run verify`、闭环测试和任务恢复测试继续通过。

### 阶段二：记忆治理和项目沉淀

目标：把“记忆建议”从单一确认按钮升级为可追溯、可拒绝、可编辑、按项目沉淀的治理流程。

实施内容：

1. 为记忆建议补充项目、会话、Run、来源类型、分类、创建时间和版本字段。
2. 固定记忆分类：项目事实、工作规则、用户偏好、经验教训、资料索引。
3. 增加建议的拒绝、编辑后批准、合并重复和查看历史能力。
4. 服务端禁止通用 `write`、`edit`、`bash` 直接修改长期记忆文件。
5. `memory_update` 只能创建待审核建议，批准操作由独立 API 完成。
6. 批准前显示来源 Run、原始依据、拟写入位置和影响范围。
7. 避免批准一条建议时无提示地覆盖整个记忆 section；改为条目级更新或要求用户确认替换。
8. 项目切换时只注入当前项目允许的记忆；全局偏好和项目记忆分开显示。
9. 增加记忆写入事件和失败恢复记录。

建议涉及文件：

- `server/agent.mjs`
- `server/index.mjs`
- `client/src/components/MemoryTab.jsx`
- 新增或调整 `server/记忆管理.mjs`

验收标准：

- Agent 无法通过普通文件工具直接写入长期记忆。
- 用户可以查看、编辑、批准、拒绝和合并记忆建议。
- 每条已批准记忆能够追溯到项目、会话和 Run。
- 项目记忆不会泄漏到另一个项目的 Agent 上下文。
- 记忆写入失败时不会把建议错误显示为已批准。

### 阶段三：项目列表、项目设置和会话沉淀

目标：让项目列表从“分类展示”升级为真正的项目管理入口。

实施内容：

1. 增加项目创建、编辑、归档、恢复和状态修改界面。
2. 保留现有项目分类：交通规划、GIS / 地图分析、调研报告、Office 文档、数据分析、综合项目、资料库。
3. 增加按类型、状态、置顶、最近活跃和待处理事项筛选。
4. 项目设置中增加默认模型、Agent Profile、允许使用的 Skills、记忆策略和成果规则。
5. 将会话、Run、成果、记忆和 Skills 配置都挂载到当前项目。
6. 会话置顶从浏览器本地状态提升为服务端持久状态。
7. 增加固定上下文快照和会话冻结，明确冻结后是否允许继续执行。
8. 会话分支保留父会话、来源消息、分支时间和分支用途。
9. 任务中心支持当前项目、全部项目、状态、模式和失败原因筛选。
10. 继续和重试创建新 Run 后，界面自动切换到新 Run，而不是继续停留在旧 Run。

建议涉及文件：

- `server/项目管理.mjs`
- `server/index.mjs`
- `client/src/components/SessionSidebar.jsx`
- `client/src/components/任务中心.jsx`
- `client/src/components/SettingsPanel.jsx`
- `client/src/api.js`

验收标准：

- 用户可以从项目列表完成创建、编辑、归档和恢复。
- 项目类型和状态对会话、任务、成果、记忆筛选均有效。
- 项目设置可以影响新 Run 的模型、Profile、Skills 和记忆策略。
- 新建、切换、分支、冻结、恢复多个会话时，旧会话和后台 Run 可见、可点击、可恢复。

### 阶段四：Chat / Agent 前端结构收敛

目标：形成清晰的“Chat 查找—Agent 执行”产品边界，同时保持已有事件流和会话管理能力。

实施内容：

1. 顶层模式收敛为 Chat 和 Agent。
2. 保留服务端 `office` 能力作为内部任务能力，但从主模式按钮中移除。
3. 将“创作模式”改为 Agent Profile，并增加创作、研究、Office、GIS、数据分析等 Profile。
4. Chat 使用独立的只读会话类型和工具白名单，允许知识库检索、Skills 检索、文档读取和用户澄清。
5. 知识库页面内置 Chat：可以针对当前资料提问、查看来源、引用原文和保存笔记。
6. Skills 页面内置 Chat：可以搜索能力、查看依赖、解释使用方式，并通过“使用此 Skill”创建 Agent Run。
7. Chat 不允许 bash、write、edit、Office CLI、地图修改和 memory_update。
8. Agent 启动前显示 Profile、模型、Skills、Office 能力和写入范围。
9. Chat 和 Agent 的消息、Run、成果和事件继续统一进入现有历史与任务中心。
10. 为 Chat 增加明确的“转为 Agent 任务”入口，保留用户选择的引用、Skill 和上下文。

建议涉及文件：

- `client/src/components/ChatPanel.jsx`
- `client/src/components/KnowledgeBase.jsx`
- `client/src/components/SkillsManager.jsx`
- `client/src/components/SettingsPanel.jsx`
- `server/task.mjs`
- `server/agent.mjs`
- 视最终复用方式补充 `/api/chat/*` 适配接口

验收标准：

- 前端默认只显示 Chat 和 Agent 两个顶层模式。
- Chat 不能修改项目文件或长期记忆。
- 从知识库或 Skills Chat 转为 Agent 后，引用和能力计划不丢失。
- Office CLI 由任务判断并记录启用原因、执行器和验证结果。
- 多个 Chat 和 Agent 会话可以并存，事件、未读数和任务状态不串线。

### 阶段五：成果验收和 Office 质量闭环

目标：让“产物生成成功”与“成果可以正式使用”分开，并提供可追溯的版本审计。

实施内容：

1. 在现有轻量结构校验基础上，增加 DOCX 内容节点、样式和页数检查。
2. 增加 XLSX 工作表、公式、关键单元格和格式检查。
3. 增加 PPTX 页面数量、文本溢出、关键元素和渲染检查。
4. 对 PDF 和图片增加渲染或可读取性检查。
5. 将验证分为结构验证、内容验证、视觉验证和人工确认四类。
6. 成果发布增加版本、来源 Run、验证结果、发布人、发布时间和回滚目标。
7. 增加成果详情、版本列表、差异摘要和回滚接口及前端页面。
8. 失败成果只能保留在 Run 中，不能进入正式成果列表。
9. Office CLI 不可用或验证不确定时，必须显示失败或待人工确认，不能显示为已完成。

建议涉及文件：

- `server/产物验证.mjs`
- `server/成果管理.mjs`
- `server/office.mjs`
- `client/src/components/SessionSidebar.jsx`
- 新增 `server/成果验收.mjs`

验收标准：

- Word、Excel、PPT、PDF 的验证结果能够区分结构、内容和视觉层级。
- 成果可以查看历史版本、来源 Run、验证结果和回滚记录。
- 一个失败或未完成的 Run 不会被固定为正式成果。
- 至少有一组真实 Office 文件回归样本通过验证。

### 阶段六：Pi Runtime 管理和 Harness 完善

目标：在不修改 Pi 内核源码的前提下，建立规聚自己的运行时控制层。

实施内容：

1. 新增 Pi Runtime 适配层，隔离 `agent.mjs` 对 Pi SDK 的直接依赖。
2. 统一管理 Runtime 创建、恢复、停止、压缩、模型切换和工具权限。
3. 为每个 Runtime 记录 provider、model、Profile、工具包版本、策略版本和健康状态。
4. 增加 Runtime 健康检查、异常标记、重启和恢复入口。
5. 为 Run 保存模型快照、Profile 快照、工具策略快照和恢复链。
6. 增加有限并发调度，避免多个 Run 无限制占用模型、Office CLI 和文件资源。
7. 增加幂等的步骤状态和可恢复检查点；不把当前 JSONL 重开误称为 token checkpoint。
8. 预留 Pi 原生 fork、原生 checkpoint 和运行回放接口，但在底层能力不足时保持明确的降级状态。
9. 增加项目级评测任务：读取可靠性、Skills 执行、Office 产出、记忆治理和并发写入。

建议涉及文件：

- `server/agent.mjs`
- `server/task.mjs`
- `server/runs.mjs`
- 新增 `server/Pi运行时管理.mjs`
- 新增 `server/运行评测.mjs`

验收标准：

- 业务模块不再直接散落调用 Pi SDK 生命周期。
- 可以查看每个 Run 使用的模型、Profile、工具策略和 Runtime 状态。
- Runtime 异常后，Run 能进入明确的 recovering / failed 状态并提供恢复入口。
- 并发上限、文件锁和 Office 资源限制能够共同生效。
- Pi 不支持的能力显示为“未支持或提示恢复”，不伪装成已完成。

### 阶段七：真实回归、发布和远程交付

目标：从“自动化检查通过”提升到“核心用户路径经过真实验证”。

实施内容：

1. 增加浏览器端多会话、切换、后台任务和未读状态回归。
2. 增加并发文件写入、取消清理、服务重启和恢复回归。
3. 增加模型超时、限流、鉴权失败和 Office CLI 不可用回归。
4. 增加真实 DOCX、XLSX、PPTX、PDF 样本的生成和验收。
5. 同步 `package.json`、README、变更日志和版本管理计划中的版本号及完成状态。
6. 形成最终变更清单、测试记录和已知边界。
7. 在用户确认后再提交、推送远程分支并核对远程仓库显示结果。

## 6. 阶段依赖

```text
阶段一：写入隔离与原子持久化
       ↓

       ↓

       ↓

       ↓

       ↓

```

阶段一是硬前置。阶段二和阶段三可以小范围并行设计，但项目设置必须使用阶段一确定的 Run、成果和记忆边界。阶段六不提前替代阶段一至五的稳定性工作。

## 7. 统一质量门槛

每个阶段完成前必须同时满足：

- 代码检查和构建通过。
- 原有事件流、会话历史和任务中心回归通过。
- 新增接口具有成功、失败、取消和重复调用测试。
- 失败状态不能被误显示为完成状态。
- 文件、成果和记忆的来源关系可追溯。
- 不把结构冒烟测试描述成真实生产验证。
- 不修改桌面端，不引入没有验收标准的额外功能。

## 8. 主要风险和处理方式

| 风险 | 处理方式 |
| --- | --- |
| 临时目录与 Office CLI 相对路径冲突 | 先做路径映射和真实 Office 样本测试，再扩大写入隔离范围 |
| 并发锁导致旧任务无法恢复 | 锁记录 Run 和心跳，服务重启时只回收确认失效的锁 |
| 记忆审批改变现有用户习惯 | 保留现有确认入口，增加审核详情，不自动写入长期记忆 |
| Chat / Agent 改版影响已有会话 | 保留旧 mode 的服务端兼容解析，前端逐步迁移 |
| Pi 原生 checkpoint 不可用 | 使用 JSONL 重开加恢复提示，并明确记录能力边界 |
| 真实 Office 验收环境不稳定 | 将 Office CLI 可用性、结构校验和视觉校验分别记录，不静默降级 |
| 变更范围过大 | 每阶段独立提交、独立测试，未通过质量门槛不进入下一阶段 |

## 9. 第一阶段立即执行清单

下一步只启动阶段一，不同时改前端产品结构。具体顺序：

1. 盘点现有所有写入入口和文件路径。
2. 设计 Run staging、锁记录和发布状态。
3. 先为 JSON / JSONL 持久化增加安全写入工具。
4. 接入 Agent、Office 和成果发布路径。
5. 增加并发、取消、异常清理和服务重启测试。
6. 运行完整验证，确认旧功能没有回归。

阶段一通过后，再进入记忆治理和项目设置，避免在写入边界不稳定时继续增加前端入口。
