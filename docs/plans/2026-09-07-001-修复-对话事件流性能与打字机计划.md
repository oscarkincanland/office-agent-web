# 修复对话事件流性能、完整性与打字机体验

## 1. 目标与非目标

本轮只解决 Web 版规聚在“发送消息后长时间无反馈、事件流不完整、历史回放不可信、文本突然整段出现、长会话逐渐变慢”上的稳定性问题。

本轮不做：

- 不改桌面端，不改 Pi 内核，不更换模型供应商。
- 不重做项目列表、知识库、地图、模板库或视觉主题。
- 不删除既有 `/api/agent/prompt`、`/api/agent/stream`、`token`、`thinking`、`tool_start` 等兼容事件。
- 不把原始模型思考、密钥、完整工具输出或无边界原始 Pi 事件永久存档。

## 2. 已确认的基线证据

### 2.1 实测链路

对 `opencode-go/deepseek-v4-flash` 发出 Chat 请求“只回答 OK，不调用工具”后：

| 阶段 | 实测耗时 | 结论 |
| --- | ---: | --- |
| 新 client 建立 SSE 至 `connected` | 1.96 秒 | 冷会话创建 Runtime 有成本；已打开页面的热连接不应重复承担。 |
| 点击发送至 HTTP `accepted` | 3.47 秒 | 模型尚未调用，主要是服务端 admission / Run 建档成本。 |
| HTTP `accepted` 至首个 token | 4.10 秒 | 属于模型首包及 Pi 回合启动；前端目前未正确呈现中间状态。 |
| `agent_end` 至 `run_finished` | 1.73 秒 | 是产物检测 / flush 收尾，不应继续显示为“连接模型”。 |

最近一次 Agent “测试一下” Run 共 53.3 秒：第一个工具事件在 Run 开始后 17.6 秒，最终文本在 50.4 秒才到。该输入被错误规划为 Office CLI 与 Skills 任务，随后读取了目录、Office 文档和 Skills；这不是前端网络卡住。

### 2.2 已确认的代码原因

1. `client/src/components/ChatPanel.jsx` 将 Agent 模式的内部说明拼接进 `fullText`；`server/task.mjs` 又对完整文本进行关键词能力判断。内部说明中含有 “skills”“Office CLI”“生成”，导致普通输入被误判。
2. `server/runs.mjs` 的 `beginRun()` 对每一轮创建完整工作区快照并复制可回滚文件；Chat 也进入该路径。实测目标工作区一次深快照约 1.24 秒。
3. `server/agent.mjs` 仅转发了 Pi 事件子集；Pi 的 `agent_start`、`turn_start/end`、队列、压缩以及 `message_update` 的 start/end/toolcall 增量没有进入应用事件流。
4. `ChatPanel` 收到 `message_start` / `message_end` 和服务端 `stats` 后没有可见处理；因此模型已开始时用户仍只看到“已接收”或“准备执行”。
5. `assistant_final` 到达时，如果页面已有任意文本 block，前端不会用最终文本校正已收 token。网络重连或 token 丢失时可能形成截断回复。
6. 现有 `requestAnimationFrame` 只合并模型 token，不是字符级打字机。模型没有 token、只给 `assistant_final` 时，长回答必然一次性出现。
7. 自动压缩只依赖进程内 `promptChars` / 最近 usage；服务重启或恢复旧 JSONL 会话后，已有长上下文不会立即触发压缩。

## 3. 设计原则

- 先让用户 100ms 内看到“服务端已受理 / 模型已开始 / 正在调用工具 / 正在收尾”的真实阶段，再优化模型首 token。
- Chat 是只读任务：不需要工作区回滚副本，不能为保障 Agent 写入安全而承担大文件扫描。
- Agent 的文件安全不退化：把“全工作区预复制”改为“首次目标写入时按文件留档”，而非取消 staging、锁或验证。
- SSE 传递所有对产品有意义且可安全展示的生命周期事件；原始大文本、敏感 provider 内容不做无上限镜像。
- `assistant_final` 是权威文本，永远可以修复丢失或重复的 token。
- 打字机仅是展示层；原始完整回复必须立即在内存中保存，不能因为动画而影响复制、历史或完成状态。

## 4. 事件模型与阶段定义

保留既有事件名称，同时补充以下统一字段：

```js
{
  id: 123,                    // session channel 单调递增
  type: "token",
  at: "2026-09-07T...Z",      // 服务端 emit 时刻
  data: {
    runId: "run_...",
    turnId: "turn_...",        // 无法取得时为 null
    sequence: 12,
    // 各事件自己的字段
  }
}
```

新增的轻量生命周期事件：

| Pi / 服务端来源 | 应用事件 | 前端用途 | 持久化策略 |
| --- | --- | --- | --- |
| HTTP admission 开始、结束 | `run_admitting`、`run_admitted` | 正确显示“准备任务” | 保存摘要和耗时 |
| Pi `agent_start` | `agent_started` | 显示“模型已开始处理” | 保存元数据 |
| Pi `turn_start/end` | `turn_started`、`turn_ended` | 折叠事件流的回合边界 | 保存元数据 |
| Pi `message_start/end` | 保留原名并携带 role / messageId | 显示“模型开始生成” | 保存边界，不保存全文 |
| Pi `text_start/end`、`thinking_start/end` | `text_boundary`、`thinking_boundary` | 流式状态与无障碍提示 | 不逐条持久化 |
| Pi toolcall delta | `tool_call_progress` | 展示“正在组织工具参数” | 只保留最后摘要 |
| Pi 工具生命周期 | 保留 `tool_start/output/end` | 工具卡片与 Todo | 保存摘要 |
| Pi usage / stats | 保留 `stats` | 显示上下文和输出统计 | 保存最后一条 |
| Pi queue / compact / retry | `agent_queued`、`context_*`、`agent_retry*` | 明确等待原因 | 保存摘要 |
| `agent_settled` | 保留 `agent_end` | 任务回答结束 | 保存 |
| Run 收尾 | 保留 `run_finished` | 显示产物检测中或完成 | 保存 |

约束：`token`、`thinking`、`tool_output` 可以实时发送，但 channel history 不得因海量增量挤掉终态事件；回放依赖最终 `assistant_final`、工具终态和阶段摘要恢复一致状态。

## 5. 分阶段实施

### 阶段 A：先加可测量性，不改业务语义

目标：能够准确回答“一次等待究竟花在何处”。

修改范围：

- `server/index.mjs`
- `server/agent.mjs`
- `client/src/components/ChatPanel.jsx`
- 新增 `scripts/对话流性能回归测试.mjs`

实施要求：

1. 为 prompt admission、Pi prompt、Pi message_start、首个 token / thinking / tool、agent_end、run_finished 记录单调时间与服务端 ISO 时间。
2. 所有 session channel event 统一写入 `id`、`at`、`runId`；`connected` 也要返回当前 cursor 和服务端时间。
3. 前端显示精简状态：`准备任务`、`模型已开始`、`生成回复`、`调用工具`、`整理产物`。状态只取真实事件，禁止用延时猜测。
4. 新增只读 API 或 Run 字段用于取得阶段耗时；不返回 API Key、完整 prompt、思考原文或完整工具输出。
5. 新脚本使用一个短 Chat 请求，输出 admission、首 Pi 事件、首文本和完成耗时；模型失败时输出结构化失败阶段。

验收：

- 浏览器在收到 `message_start` 后立刻从“已接收”切换为“模型已开始”。
- 一个 Run 可以读取 admission、首模型事件、首可见内容与收尾耗时。
- 现有 SSE 重连游标、Run 过滤和 Todo 轮询不回归。

### 阶段 B：去掉误判与无效 admission 开销

目标：普通 Chat / 简单 Agent 不再因内部说明被误触发 Office、Skills 或全工作区备份。

修改范围：

- `client/src/components/ChatPanel.jsx`
- `server/index.mjs`
- `server/task.mjs`
- `server/runs.mjs`
- `server/写入协调.mjs`
- `server/agent.mjs`

实施要求：

1. 前端将用户原文 `rawText` 与 UI 说明分离：
   - `text` 只传用户原文、当前文件标识、显式引用、显式附件。
   - `task.mode`、`task.currentFile`、`task.references` 保持结构化字段。
   - 禁止把 `MODE_META.prefix` 当作能力规划的输入；如仍需给模型说明，改由服务端按 mode 注入，不参与 `planTaskCapabilities()`。
2. `planTaskCapabilities()` 只对用户原文、显式附件、引用和 currentFile 判断 Office / Skills；“测试一下”不得得到 `officecli: preferred` 或 `skills: preflight`。
3. 为 `beginRun()` 增加明确的快照策略：
   - Chat Run 使用 `snapshotMode: "none"`：保留 Run、事件、历史和任务中心记录，但不深扫描、不复制 before blobs。
   - Agent Run 使用 `snapshotMode: "deferred"`：创建轻量 manifest / staging，但不在 admission 时扫描并复制整个工作区。
4. 在 `stageWrite()` / 首次目标文件锁定处建立“按目标文件的 before 副本”。同一路径在一个 Run 内只存一次；新增文件只记录“之前不存在”。
5. 发布、回滚和产物验证改为读取目标文件的延迟快照。不得破坏现有 staging、文件锁、取消清理、发布验收。
6. 如果某个未迁移的写入路径无法做目标级快照，明确回退到完整快照并发送 `snapshot_fallback` 事件；不能静默失去回滚能力。

验收：

- Chat 发送后不执行深工作区 snapshot / `copyBeforeBlobs`。
- 简单 Agent “测试一下”不触发 Office CLI 检查、Skills 搜索或文档读取。
- Agent 修改已有文件后仍可以回滚；Agent 新建文件后回滚会删除该文件。
- 本地短 Chat admission 的 p95 目标低于 750ms；该指标不包含模型首 token。
- 并发写入、取消、恢复、成果发布的既有回归仍通过。

### 阶段 C：补齐安全的 Pi 事件映射与可恢复事件流

目标：事件流完整反映执行状态，断线和历史回放不会造成截断或“没有过程”。

修改范围：

- `server/agent.mjs`
- `server/index.mjs`
- `server/runs.mjs`
- `server/事件存储.mjs`
- `client/src/components/ChatPanel.jsx`

实施要求：

1. 按第 4 节映射 Pi 的 agent、turn、message、toolcall、queue、compaction、retry、stats 生命周期；保留原有事件兼容性。
2. 每个 `message_update` 的 `text_delta`、`thinking_delta` 继续发送；对 start/end/toolcall delta 发送轻量事件，不发送未裁剪原始 event 对象。
3. 修复 index 层 `emitChannel()` 与 agent 层 `emitChannelSafe()` 的字段不一致：两个入口都自动补齐 `runId`、`at` 和 event id。
4. 按事件类别分层：
   - session replay：保留最近 token / thinking 增量的有限窗口、所有未完成工具、最后 `assistant_final` 和全部终态。
   - Run 历史：保存阶段、工具、错误、统计和最终回答；不存每个 token。
5. `assistant_final` 到达时以它为权威：若当前累计文本不同，替换或补齐为最终文本；不得因已有部分 token 而忽略 final。
6. 断线重连后，若游标落后于 delta 保留窗口，服务端先发 `stream_resync`，客户端用最终文本和工具终态重建，不显示失败或重复消息。

验收：

- 人为丢弃中间 token 后，`assistant_final` 仍使最终对话全文正确。
- 多工具并行时，工具卡按 `toolCallId` 正确归属，不互相覆盖。
- 前端能显示模型开始、工具准备、工具输出、重试、压缩、收尾等状态，默认折叠，避免对话被事件淹没。
- SSE 重连、切换子会话和历史恢复后，不串 Run、不重复系统消息、不丢最终回答。

### 阶段 D：实现真正的打字机展示与流式渲染保护

目标：无论供应商按 token 流式还是一次性给 final，用户都看到连续、快速、不卡顿的文字出现。

修改范围：

- `client/src/components/ChatPanel.jsx`
- `client/src/components/MarkdownBody.jsx`
- `client/src/styles.css`
- 新增 `client/src/components/流式文本队列.js`

实施要求：

1. 建立“真实文本”和“展示文本”两套状态：
   - token / final 先写入真实文本缓冲；复制、历史保存和完成状态使用真实文本。
   - 展示队列以每帧有限字符数推进；速度默认约 35–60 汉字/秒，并根据 backlog 自适应加速，最终不允许拖慢完成超过 300ms。
2. token 正常流式时，将每批 token 拆入展示队列；`assistant_final` 只补差异，不能重复展示。
3. 没有 token、只有 `assistant_final` 时，将 final 全文送入同一展示队列，解决整段跳出。
4. 流式中使用轻量文本节点或简化 Markdown；完整 `ReactMarkdown + KaTeX + highlight` 仅在 120–180ms 防抖后或结束时渲染，避免每一帧重解析整段 Markdown。
5. 工具开始、结束、错误、停止或新回合开始必须立即 flush / cancel 正确队列，避免文本跑到另一个会话。
6. 尊重 `prefers-reduced-motion`：关闭逐字动画，仍按批次快速呈现。

验收：

- 600 字仅 final 的回答不会整段闪现；视觉上连续出现，实际完整文本已立即可复制。
- 10,000 字流式回答页面无明显掉帧、无 React error、无重复段落。
- 停止、重连、切换会话后不会继续向旧会话追加文字。
- 打字机关闭或减少动态效果时，最终文本和产物状态与默认模式一致。

### 阶段 E：约束上下文膨胀与恢复会话首轮

目标：长会话在服务重启、项目切换和工具密集任务后仍保持可预期首响应。

修改范围：

- `server/agent.mjs`
- `server/Pi运行时管理.mjs`
- `server/项目管理.mjs`（如项目 Profile 需存阈值）
- `client/src/components/ChatPanel.jsx`

实施要求：

1. 将稳定不变的工作区规则保留在 `.agent-context.md` / session 资源中；`buildDynamicContext()` 每轮仅注入当前文件、显式引用、必要的项目记忆摘要，禁止重复注入长篇 Office / 写入规则。
2. Chat 使用更短的动态上下文和只读工具策略；Agent 才注入完整任务封装与产物规则。
3. 自动压缩的判断不得仅依赖本次 Node 进程的 `promptChars`：恢复 JSONL 后应读取 Pi 可用 usage / session 状态；若 Pi 没有可靠 token 数，标记为“估算”并提供明确的手动压缩入口。
4. 在模型 prompt 前触发压缩，而不是模型已开始后才压缩；压缩过程必须通过事件流显示，且不能与正在执行的 Agent 回合并发。
5. 为每次 Run 记录“注入上下文字符数、最近输入 token、是否压缩、压缩耗时”；不得记录完整私密内容。

验收：

- 服务重启后恢复一个长会话，首轮会先做上下文预算判断而不是盲目累积 90,000 字后才压缩。
- Chat 的动态注入明显少于 Agent，且原有引用、当前文件和记忆边界不丢失。
- 自动压缩失败时模型调用仍有明确状态、可重试边界和用户可见提示。

### 阶段 F：回归、性能对比与发布门槛

目标：证明改造没有只改善演示，而是覆盖真实产品链路。

新增 / 修改测试：

- `scripts/对话流性能回归测试.mjs`
- `scripts/事件流断线恢复测试.mjs`
- `scripts/打字机展示浏览器测试.mjs`
- 现有 `npm.cmd run verify`
- 现有 `npm.cmd run test:final`

必须覆盖：

1. Chat 短问答：不触发 Office / Skills / 深快照，记录完整阶段时间。
2. Agent 只读任务：不误判 Office / Skills；能显示模型与工具阶段。
3. Agent 文档修改：首次写入留下目标 before 副本，发布与回滚正确。
4. 模型只发 final、正常 token 流、thinking + tool、工具并行、模型超时、Pi retry。
5. SSE 中途断开并重连；浏览器切换会话再切回；历史恢复；最终文本一致。
6. 10,000 字打字机、停止、减少动态效果和页面性能检查。
7. 长会话恢复、自动压缩、压缩失败与手动压缩。

发布门槛：

- `npm.cmd run verify` 与 `npm.cmd run test:final` 均通过。
- 新增服务端时序测试、断线恢复测试和浏览器测试通过。
- 真实模型测试至少覆盖一条 Chat 和一条 Agent；报告中分别列出 admission、首可见事件、首文本、完成耗时。
- 未经用户确认不得更改模型凭据、推送远程仓库或删除历史 Run / 会话数据。

## 6. 推荐的交接顺序

不要让多个模型同时修改 `server/agent.mjs` 或 `ChatPanel.jsx`。

1. 模型 A：阶段 A，先提交“只增加时序字段与观测”的小提交。
2. 模型 B：在 A 的基础上完成阶段 B；重点验证 Chat admission 和 Agent 文件回滚。
3. 模型 C：在 B 的基础上完成阶段 C；先写断线 / final 权威回归，再改事件映射。
4. 模型 D：在 C 的基础上完成阶段 D；只改前端展示和浏览器测试。
5. 模型 E：完成阶段 E、F，运行全量回归并产出对比报告。

每个模型只提交自己阶段的文件，提交前必须先执行 `git diff --check`、`npm.cmd run verify` 和该阶段对应脚本。

## 8. 风险与禁止项

| 风险 | 处理方式 |
| --- | --- |
| 为提速取消 Agent 回滚 | 禁止；必须改为首次目标写入留档。 |
| 全量转发 Pi 原始 event 导致内存和隐私泄漏 | 只映射安全、可展示的生命周期字段；限制 delta replay。 |
