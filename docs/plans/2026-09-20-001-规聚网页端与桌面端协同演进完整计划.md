# 规聚网页端与桌面端协同演进完整计划

## 1. 执行摘要

本计划以当前 `office-agent-web` 仓库为唯一主仓库，不再平行维护一套独立桌面端业务代码。网页端与 Electron 桌面端共用 React 界面、领域服务、Pi Runtime 适配、会话与 Run 数据模型、权限规则、事件协议、工作区与成果管理；两个端只在平台入口和操作系统能力上分开。

目标形态不是“把网页套进 Electron”，也不是“一次性重写现有系统”，而是先把当前 Express 路由、Agent 运行时和前端通信中的平台耦合抽成稳定边界，再形成：

```text
                         ┌────────────────────┐
                         │   共享 React 应用   │
                         │  页面、组件、状态层  │
                         └─────────┬──────────┘
                                   │ 平台桥接
                  ┌────────────────┴────────────────┐
                  │                                 │
        ┌─────────▼─────────┐             ┌─────────▼─────────┐
        │ 网页端适配器       │             │ 桌面端预加载桥     │
        │ HTTP + SSE         │             │ 版本化 IPC         │
        └─────────┬─────────┘             └─────────┬─────────┘
                  │                                 │
        ┌─────────▼─────────┐             ┌─────────▼─────────┐
        │ Express 网页服务   │             │ Electron 主进程    │
        │ 认证、路由、静态资源│             │ 窗口、系统能力、权限│
        └─────────┬─────────┘             └─────────┬─────────┘
                  │                                 │
                  └──────────────┬──────────────────┘
                                 ▼
                     ┌──────────────────────┐
                     │ 共享应用服务与 Agent  │
                     │ Host / Worker        │
                     ├──────────────────────┤
                     │ 工作区与文件代理      │
                     │ 会话、Run、成果、记忆 │
                     │ 权限与凭据代理        │
                     │ 事件总线与恢复        │
                     │ PiRuntimeManager     │
                     │ BrowserController    │
                     └──────────────────────┘
```

总体策略：

1. 先稳定当前 v0.11.2 基线，清理“文档版本落后于代码”和未验证变更。
2. 以服务边界抽取代替大规模目录重写，保证网页端持续可发布。
3. 建立同一套能力协议，网页端走 HTTP/SSE，桌面端走 IPC/JSON-RPC。
4. 桌面端先完成可用壳和真实模型闭环，再替换内置浏览器显示层。
5. 桌面端浏览器使用 Electron `WebContentsView`；网页端浏览器保留 Agent 自动化、外部可见接管与截图兜底，不追求伪装成原生浏览器。
6. 每个阶段都必须同时交付网页端回归、桌面端增量和共享协议测试，不允许“桌面端先分叉、以后再合并”。

## 2. 当前基线与问题证据

### 2.1 当前技术基线

- 当前包版本：`0.11.2`。
- 前端：React 18 + Vite 5。
- 服务端：Express 5，Node.js 22 及以上。
- Agent：`@earendil-works/pi-coding-agent 0.85.1`。
- 当前启动方式：PowerShell 启动 `server/index.mjs`，固定使用本地端口。
- 当前桌面能力：没有 Electron 主进程、预加载桥、IPC 协议和桌面打包配置。
- 当前测试：已存在稳定性、事件协议、运行轨迹、记忆准入、工作区隔离、联网搜索和内置浏览器测试入口。

### 2.2 当前结构性负担

当前代码已具备较完整产品能力，但平台边界过度集中：

- `server/index.mjs` 约 4221 行，包含约 207 个路由注册点，路由、进程入口、业务编排和平台操作混合。
- `server/agent.mjs` 约 2850 行，承载会话、工具、Pi Runtime、工作区、审批和事件等多种职责。
- `server/内置浏览器.mjs` 约 947 行，手写 CDP 连接、浏览器进程、截图流、用户输入和 Agent 操作。
- 前端仍直接感知 HTTP/SSE 细节，尚无统一的平台能力桥。
- `REQUIREMENTS.md` 和 `DESIGN.md` 仍声明较早基线，与当前 v0.11.2 有版本漂移。
- 当前工作区存在多处未提交修改，主要覆盖浏览器、对话、Pi Runtime 和服务入口；桌面迁移前必须先形成可复现基线。

### 2.3 当前内置浏览器的根本限制

现有网页端浏览器默认启动系统 Edge/Chrome 的 headless 模式，通过 CDP 截图流显示，并把用户坐标输入转发给页面。该方案可以作为 Agent 自动化和远程观察通道，但无法成为高质量人工浏览器：

- 用户看到的是帧流，不是真实页面表面。
- 坐标点击、输入焦点、缩放和文本选择容易漂移。
- 标签页、弹窗、下载、权限、登录和快捷键体验不完整。
- 页面导航后元素引用容易过期。
- 用户操作和 Agent 操作缺少严格队列、代际和所有权管理。
- 浏览器进程、端口和退出回收存在孤儿进程与资源抖动风险。

因此，本计划不再以“继续提高截图帧率”作为主要方向，而是把浏览器拆成共享控制协议和平台显示实现。

## 3. 产品目标、范围与边界

### 3.1 总体目标

在保持网页端持续可用的前提下，交付一个 Windows 优先、可便携运行、无需用户预装 Node.js 或 Pi CLI 的 Electron 桌面端，并建立可长期维护的双端共享架构。

### 3.2 双端关系

网页端和桌面端保持“业务结果平权”，但不要求“平台表现完全相同”：

- 两端都能完成对话、文件、Office、知识库、地图、工作流、Run、成果、记忆、联网搜索和 Agent 浏览器任务。
- 桌面端额外拥有原生窗口、系统文件选择、系统安全存储、后台任务、托盘、原生浏览器视图、安装和更新能力。
- 网页端保留轻量访问、局域网部署和开发调试价值。
- “同步推进”指同一主仓库、同一共享核心、同一版本能力矩阵，不等同于本阶段建设云账户或跨设备实时同步。

### 3.3 本计划范围

- 共享领域服务与平台适配层。
- React 界面双端复用。
- Express 网页端持续演进。
- Electron 主进程、预加载桥和 Agent Host。
- Pi 模型、供应商、会话和工具能力统一。
- 网页端与桌面端内置浏览器重构。
- 工作区、凭据、权限、记忆和成果安全边界。
- 数据迁移、便携包、安装包、升级和回滚。
- 双端测试矩阵、性能门槛和发布治理。

### 3.4 暂不纳入首个正式版

- 移动端。
- 公有云多租户和账号系统。
- 跨设备实时数据同步。
- 任意第三方 OMP 插件直接在主进程执行。
- macOS/Linux 正式支持；架构保持可扩展，但首轮只验收 Windows。
- 一次性将全部 JavaScript 改写为 TypeScript。
- 与桌面化无关的大规模视觉重构。

### 3.5 受影响角色

| 角色 | 主要变化 | 需要保障 |
| --- | --- | --- |
| 规划业务用户 | 可在网页或桌面完成同一项目任务 | 文件与成果不丢失、升级可恢复、操作路径稳定 |
| 高级用户 | 获得桌面原生浏览器、后台任务和本地能力 | 权限可见、行为可审计、浏览器可接管 |
| 开发者 | 从单一 Web 进程转为共享核心和双平台适配 | 接口边界清楚、合同测试可复用、避免双份修复 |
| 发布维护者 | 增加便携包、安装包和更新链路 | 构建可复现、版本可回滚、数据兼容 |
| 安全审查者 | 需要审查凭据、文件、浏览器和插件边界 | 默认拒绝高风险能力、日志脱敏、审批可追踪 |

## 4. 方案选择与被拒绝方案

### 4.1 采用方案：单主仓库、共享核心、双平台适配

原因：

- 最大化复用现有 React、Pi Runtime、工作区、知识库、地图和 Office 能力。
- 网页端可持续交付，不需要等待桌面端完成。
- 业务规则只有一个事实来源，减少权限、事件和数据模型分叉。
- 平台差异集中在 HTTP/SSE、IPC、文件选择、安全存储和浏览器显示层。

### 4.2 不采用：独立桌面仓库长期平行开发

原因：业务逻辑、供应商目录、权限和会话模型会持续复制；每次修复都需要双重移植，最终难以证明能力一致。

### 4.3 不采用：只给现有网页套 Electron 外壳

原因：虽然启动快，但会继续依赖固定端口、PowerShell 监督进程和截图浏览器，也无法形成可靠的凭据隔离、后台任务和桌面生命周期。

### 4.4 不采用：立即重写全部服务

原因：当前系统已有大量可用能力和回归脚本。重写会同时失去行为基线和可比较证据，风险高于渐进抽取。

## 5. 目标架构

### 5.1 共享应用服务

从现有服务端逐步抽出以下稳定边界，网页和桌面共同调用：

| 服务 | 单一职责 | 主要来源 |
| --- | --- | --- |
| 对话服务 | 消息、上下文、模式和会话关系 | `server/agent.mjs`、会话路由 |
| 智能体编排器 | Run 生命周期、工具调用、取消、继续、重试 | AgentManager、runs、事件存储 |
| Pi 运行时管理器 | create/resume/fork、模型、thinking、资源重载 | `server/Pi运行时管理.mjs` |
| 工作区代理 | 路径解析、允许根、锁、快照、文件变更归属 | workspace、写入协调 |
| 权限服务 | 模式策略、审批、危险操作和来源解释 | 审批策略、task |
| 凭据代理 | 模型和搜索凭据引用，不向渲染层暴露明文 | Pi 配置管理、桌面安全存储 |
| 事件总线 | 统一事件信封、序号、重放、未读和前端投影 | 事件协议、事件存储 |
| 成果管理器 | Run manifest、校验、发布、版本和回滚 | 成果管理、产物验证 |
| 浏览器控制器 | 导航、观察、动作、标签页、下载和策略 | 内置浏览器、桌面浏览器代理 |

抽取原则：

- 路由和 IPC 只做输入校验、身份/工作区绑定、调用服务和错误映射。
- 共享服务不直接依赖 Express、Electron 或 React。
- 继续使用现有 ESM/JavaScript，协议校验沿用 TypeBox，避免同时进行语言迁移。
- 每次只抽一个能力域，并保留原路由兼容层。

### 5.2 网页端形态

```text
React → 平台桥接 → HTTP/SSE → Express 适配器 → 共享应用服务
```

网页端继续承担：

- 浏览器访问和局域网部署。
- 开发调试与快速发布。
- HTTP API、SSE 事件和静态资源。
- Agent 浏览器自动化、状态观察和外部接管入口。

### 5.3 桌面端形态

```text
React Renderer
  → 预加载桥（白名单、版本化 IPC）
  → Electron 主进程
  → Agent Host / Worker（版本化 JSON-RPC）
  → 共享应用服务与 Pi Runtime
```

硬性边界：

- Renderer 不直接访问 Node.js、文件系统、Pi 对象或密钥。
- `nodeIntegration=false`、`contextIsolation=true`、`sandbox=true`。
- 主进程只负责窗口、系统能力、权限代理和子进程生命周期。
- Agent Host 承担长任务，窗口关闭不等于任务进程立即消失；用户明确退出应用时才按策略等待、取消或持久化恢复点。
- Host 与主进程使用带 `protocolVersion/requestId/sessionId/runId/sequence/capabilities` 的协议。
- 密钥通过 Electron `safeStorage` 保存，Host 仅通过 `credentialRef` 请求短时使用。

### 5.4 前端平台桥接

新增统一前端能力层，现有组件不再直接拼接所有 `/api` 地址：

```text
平台桥接
├─ 对话与事件
├─ 文件和工作区
├─ 会话与 Run
├─ 模型与供应商
├─ 浏览器
├─ 设置和凭据状态
└─ 系统能力
```

网页实现调用 HTTP/SSE，桌面实现调用预加载桥。组件只消费统一返回结构和事件信封。

### 5.5 数据与存储边界

| 数据 | 网页端 | 桌面端 | 规则 |
| --- | --- | --- | --- |
| 工作区原文件 | 用户选择的工作区 | 用户选择的工作区 | 两端共享格式，不自动复制 |
| Run、事件、成果索引 | 工作区 `.oaw` | 工作区 `.oaw` | 带 schemaVersion，可迁移 |
| 应用设置 | 当前配置目录 | `app.getPath('userData')` | 与项目数据分离 |
| API Key | 服务端凭据存储 | `safeStorage` | 不进 Renderer、日志或普通 JSON |
| 浏览器 Profile | 当前项目 Profile | userData 下按工作区哈希分区 | 不写入 Git，不跨工作区串用 |
| 日志与崩溃信息 | 运行日志目录 | userData 日志目录 | 默认脱敏、限制保留周期 |

同一工作区被网页服务和桌面 Host 同时打开时，必须使用工作区写锁和进程所有者记录。无法取得写锁的一端进入只读或要求用户确认接管，禁止静默并发写入。

### 5.6 建议代码落点

以下是目标结构，不要求一次性搬迁；每个目录应随着对应服务抽取逐步建立。新增业务文件遵守中文命名要求。

```text

│  ├─ 权限服务.mjs
│  ├─ 凭据代理.mjs
│  ├─ 事件总线.mjs
│  ├─ 成果管理器.mjs
│  └─ 浏览器控制器.mjs
├─ 网页端适配/
│  ├─ 接口控制器.mjs
│  ├─ 事件流适配器.mjs
│  └─ 浏览器适配器.mjs
```

## 6. 双端能力矩阵

| 能力 | 共享实现 | 网页端 | 桌面端 | 首发要求 |
| --- | --- | --- | --- | --- |
| 对话、模型、推理强度 | PiRuntimeManager、对话服务 | HTTP/SSE | IPC/Host | 双端一致 |
| 文件与 Office | 工作区代理、officecli 适配 | 上传、路径选择 | 原生文件选择、拖放 | 双端一致 |
| 知识库与地图 | 现有领域服务 | 浏览器渲染 | 同一 React 组件 | 双端一致 |
| 会话、Run、成果 | 共享数据模型和事件总线 | 服务端持久化 | Host 持久化 | 双端一致 |
| 记忆审批 | 建议、审阅、应用三段式 | 网页审批卡 | 桌面审批卡/通知 | 双端一致 |
| 搜索与网页读取 | 统一搜索适配器 | 服务端调用 | Host 调用 | 双端一致 |
| Agent 浏览器工具 | BrowserController 协议 | Playwright/CDP 后端 | WebContentsView/CDP 后端 | 结果平权 |
| 人工浏览器体验 | 平台特定 | 外部可见窗口或扩展接管；截图兜底 | 原生 WebContentsView | 允许差异 |
| 密钥保存 | credentialRef | 服务端安全存储 | safeStorage | 不泄露明文 |
| 后台任务 | Run 与事件恢复 | 服务进程存续 | Host 存续、托盘提示 | 双端一致 |
| 更新发布 | 版本清单 | Web 部署 | 安装包/便携包/更新器 | 平台特定 |

## 7. Agent 原生能力约束

每个阶段都必须检查以下项目：

- **能力平权**：用户在界面能完成的业务结果，Agent 必须有对应原子工具或组合路径。
- **原子工具**：读、写、编辑、搜索、浏览、发布和回滚是能力，不把整套业务判断硬编码为单个工作流工具。
- **可组合性**：新增规划工作流优先通过提示、Skill 和工具组合实现。
- **共享工作区**：Agent 和用户操作同一工作区，但所有路径都经过工作区代理。
- **显式完成**：Run 通过明确完成/失败/等待状态收口，不依赖“没有新工具调用”猜测完成。
- **部分完成与恢复**：长任务保存步骤、事件和产物检查点。
- **动态上下文**：每轮注入工作区、打开文件、可用工具、Skills、模型能力和权限状态。
- **Agent 到界面实时反馈**：共享事件总线驱动双端状态，不允许后台写入后界面静默不更新。
- **完整 CRUD**：会话、项目、工作流、成果和浏览器标签等产品对象应有完整生命周期。
- **审批与可逆性匹配**：只读操作默认放行，写入、提交、发布、删除和外部副作用按风险审批。

## 8. 工作流拆分与并行关系

### 8.1 共享核心工作流

负责协议、服务抽取、Pi Runtime、工作区、事件、权限、成果和迁移。它是所有其他工作流的前置依赖。

### 8.2 网页端工作流

负责 HTTP/SSE 适配、现有功能回归、网页浏览器后端和渐进发布。每个共享服务抽取都必须先通过网页端兼容适配。

### 8.3 桌面端工作流

负责 Electron 主进程、预加载桥、Agent Host、系统能力、安全存储、桌面浏览器、打包和更新。

### 8.4 浏览器专项工作流

负责 BrowserController、AX 观察、代际引用、操作队列、用户/Agent 所有权、下载、站点策略和资源回收。网页和桌面分别实现显示与进程适配。

### 8.5 质量与发布工作流

负责协议合同测试、双端端到端测试、性能与孤儿进程检查、干净机器、中文路径、数据迁移、安装和回滚。

并行原则：最多四条工作流并行；共享协议变更必须先合入并固定版本，平台实现不得各自发明字段。

### 8.6 关键路径与并行窗口

```text
P0 基线
  └─ P1 共享协议与服务
       ├─ P2 桌面 Alpha
       │    └─ P3 桌面原生浏览器
       ├─ P3 网页浏览器治理
       └─ P4 双端产品对象与长任务
                 └─ P5 安全、打包与 Beta
                           └─ P6 正式版产品化
```

| 前置门槛 | 可并行工作 | 禁止提前进行 |
| --- | --- | --- |
| P0 验证通过 | 协议设计、Host 隔离原型 | 批量迁移路由、正式打包 |
| P1 首个合同稳定 | 桌面壳、网页平台桥、浏览器控制协议 | 分别复制业务服务 |
| P2 Host 闭环通过 | 桌面浏览器、长任务、网页浏览器治理 | 自动更新、插件市场 |
| P3 浏览器安全通过 | P4 产品能力、P5 打包预研 | 默认开放外部提交和上传 |
| P4 数据模型稳定 | 干净机器、安装升级、性能压测 | 正式版数据格式冻结 |

- 桌面空闲 60 秒后 CPU 目标低于 2%，最终阈值以 P0 基线校准。
- 浏览器面板隐藏后停止高频帧流。
- Agent 事件本地转发延迟单独统计，不把模型网络时间计入 UI 延迟。
- 连续 20 次启动、任务、退出后无 Node、Electron、Edge/Chrome 或 Host 孤儿进程。
- 长任务至少运行 60 分钟，验证事件有界、内存不持续无界增长。
- 多工作区测试不得出现路径、事件、成果和浏览器 Profile 串用。

### 11.6 发布验证

- `npm.cmd run verify`。
- 当前专项测试脚本全部通过。
- 网页与桌面构建均通过。
- `git diff --check` 通过。
- 干净虚拟机和至少一台真实 Windows 机器验收。
- 静态构建、ZIP/XML 检查不得冒充视觉和真实交互验收。

## 12. 系统级失败传播与恢复

| 失败来源 | 传播方式 | 用户看到 | 恢复策略 |
| --- | --- | --- | --- |
| 模型供应商失败 | PiRuntimeManager 标准错误 | 供应商、模型、可重试原因 | 连接测试、显式重试，不静默换模型 |
| Host 崩溃 | 主进程健康监测 | 任务中断/恢复中 | 限频重启、事件重放、创建恢复 Run |
| 网页服务崩溃 | 启动器和日志 | 服务不可用 | 防重复实例、端口所有权、手动诊断入口 |
| 工作区失效 | 工作区代理 | 路径不可用/只读 | 重新授权或切换工作区 |
| 权限拒绝 | 权限服务 | 拒绝原因与影响范围 | 修改规则或单次批准 |
| 浏览器超时 | BrowserController | 当前动作失败、页面仍保留 | 重新观察、重连调试器、用户接管 |
| 写入中断 | 原子写入与 Run 记录 | 部分完成 | 临时文件清理、回滚、恢复 Run |
| 升级失败 | 更新器 | 保持旧版本 | 校验失败不替换、回退上一版本 |

## 13. 风险登记与缓解

| 风险 | 等级 | 缓解措施 |
| --- | --- | --- |
| 当前未提交改动与迁移交叉污染 | 高 | P0 先分组、验证和固定基线；不覆盖现有改动 |
| `server/index.mjs` 一次拆分过大 | 高 | 按能力域逐个抽取，保留兼容路由和合同测试 |
| Web/Desktop 出现双份业务逻辑 | 高 | 平台层只做适配，领域规则进入共享服务 |
| Pi SDK 升级破坏行为 | 高 | PiRuntimeManager 隔离、锁版本、真实模型回归 |
| 浏览器提示注入和外部副作用 | 高 | 外部内容标记、危险操作审批、站点策略、审计 |
| 桌面凭据泄露 | 高 | safeStorage、credentialRef、日志脱敏、Renderer 隔离 |
| Host/浏览器孤儿进程 | 高 | 进程所有权、退出握手、限频重启、连续生命周期测试 |
| Web 与桌面同时写同一工作区 | 高 | 跨进程写锁、所有者记录、只读降级和接管确认 |
| Electron 包体积和启动性能 | 中 | 延迟加载地图/Office/浏览器，按阶段记录基线 |
| Office CLI 外部依赖 | 中 | 启动自检、版本提示、无 Office 任务可继续使用 |
| 便携包中的密钥迁移误解 | 中 | 密钥机器绑定，迁移后重新授权，界面明确说明 |
| 文档再次落后于代码 | 中 | 每阶段验收要求同步更新需求、设计、变更日志和能力矩阵 |

## 14. 分支、提交与兼容策略

- 当前未提交修改先完成归属和验证，不执行强制重置或覆盖。
- 桌面化工作从已验证基线创建 `codex/` 前缀分支。
- 每个阶段按“共享协议 → 网页适配 → 桌面适配 → 测试与文档”顺序提交。
- 协议字段只允许向后兼容增加；破坏性调整必须提升 protocolVersion 并提供迁移说明。
- 数据迁移必须幂等，执行前生成可恢复备份，并记录迁移版本。
- 功能未完成时使用能力协商和功能开关，不保留永久双实现。
- 每个里程碑形成可回滚标签，不把多个阶段积压到一个超大提交。
