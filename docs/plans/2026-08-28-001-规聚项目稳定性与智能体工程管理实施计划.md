# 规聚项目稳定性与智能体工程管理实施计划

## 1. 计划结论

本计划用于把当前 `office-agent-web` 从“具备 Pi Agent、Office、知识库和地图能力的工作台”，逐步提升为“面向规划生产的稳定 Agent Harness”。

本次确定的方向是：

```text
知识库 Chat       → 查资料、问问题、找来源
Skills Chat       → 找能力、选 Skill、检查输入
Agent             → 调用工具、修改文件、执行任务
Harness           → 管理项目、会话、运行、权限、产物、验证和记忆
Pi                → 提供 Agent Runtime，不直接承担整个工程管理平台
```

本计划不包含桌面端，不要求修改 Pi 内核，不重写当前对话流和事件流的用户交互形式。首要目标是提高以下四项稳定性：

1. Agent 对话和任务状态稳定。
2. Skills 发现、加载和调用稳定。
3. 文档、附件和知识库读取稳定。
4. Word、Excel、PPT、Markdown、地图分析等产物生成稳定。

同时建立项目列表分类、会话固定、项目记忆和工作成果沉淀机制。

## 2. 已确认的产品决策

这些决策来自前几轮调研和讨论，后续实现不再反复改变方向。

### 2.1 暂不做桌面端

- 保持当前 React/Vite + Express + Pi SDK 的 Web 架构。
- 不做 Electron、Agent Host、Sidecar 和跨窗口后台运行。
- 先把 Web 端的数据模型、稳定性和权限边界做好。
- 桌面化只保留为未来适配方向，不作为当前项目依赖。

### 2.2 保留现有对话流和事件流体验

保留现有：

- thinking 块。
- 工具调用块。
- 最终回答块。
- `ask_user` 追问。
- SSE 流式输出。
- abort、compact、retry、steer 和排队。
- TaskEnvelope、Run 快照、文件差异和回滚入口。

只做内部稳定性增强：

- 事件增加统一归属字段。
- 工具输出严格按 `toolCallId` 更新。
- 断线重连和重复事件幂等。
- Run 状态与前端状态一致。
- 错误、恢复和文件生成失败明确反馈。

### 2.3 Chat 和 Agent 分工

前端用户可见的顶层模式只保留两种：`Chat` 和 `Agent`。当前的“Office CLI 模式”和“创作模式”不再作为第三、第四种并列运行模式。

- `Chat` 是只读的理解、检索和问答。
- `Agent` 是可以执行工具、修改文件和生成成果的运行模式。
- “Office CLI”是 Agent 的内部能力，不是用户必须选择的模式。
- “创作模式”是 Agent 的一个 Profile / 工作流配置，不是独立内核。

#### Chat

Chat 是只读的理解和检索能力，主要放在：

- 知识库页面。
- Skills 搜索页面。
- 资料、文件和来源分析页面。

Chat 默认不能：

- 写文件。
- 执行 bash。
- 修改 Office 文件。
- 修改地图数据。
- 修改项目记忆。

#### Agent

Agent 是项目工作台的执行能力，允许在权限范围内：

- 调用 Office、KB、地图和文件工具。
- 执行规划工作流。
- 修改和生成文件。
- 创建 Run 和 Artifact。
- 等待用户确认后继续任务。

### 2.4 项目是最高层容器

后续所有资源都要归属于项目：

```text
项目
├─ 工作区
├─ 会话
├─ Agent Run
├─ 知识库
├─ Skills 配置
├─ 项目记忆
└─ 工作成果
```

### 2.5 记忆必须经过用户确认

- Agent 可以识别可能值得沉淀的信息。
- 但不能每轮对话自动写入长期记忆。
- 先生成“待沉淀卡片”。
- 用户确认、编辑、合并或拒绝后才写入项目记忆。

### 2.6 Pi 的定位

使用 Pi 官方 SDK 能力，不直接修改 Pi 内核源码。

计划新增稳定的 Pi 适配边界，未来可以管理：

- session 创建、恢复、分支、销毁。
- prompt、steer、abort、compact、retry。
- model、thinking level、工具和资源。
- Pi 事件转为项目事件。

安全、权限、文件边界、任务恢复、产物、验证和记忆由项目自身负责。

### 2.7 Office CLI 和创作模式的最新收敛方案

#### 用户看到的两层结构

```text
用户可见模式：Chat / Agent
                         ↓
Agent Profile：创作 / Office / Research / GIS / Data
                         ↓
内部能力：officecli / kb / map / file / memory / document
```

#### Office CLI 的定位

Office CLI 可以内置，但不建议继续作为前端模式按钮。它应当成为后端的文档执行器，由任务规划和能力预检判断是否调用。

用户只需要表达任务：

- “读取这个 Word 文档并提取目录。”
- “修改表格中的字段并另存为新文件。”
- “生成一份可打开的 PPT。”
- “检查这个 Excel 是否有格式问题。”

系统再决定是否启用 Office 能力。

判断不能只依赖模型自由发挥，而应采用“规则预检 + Agent 决策 + 执行后验证”三层机制：

```text
用户任务
  ↓
任务预检：文件类型、动作、输出格式、当前项目
  ↓
能力计划：是否需要 Office / KB / 地图 / 普通文件能力
  ↓
Profile 和权限检查
  ↓
仅注册本次允许的工具
  ↓
Agent 执行
  ↓
Office / 文件格式 / 产物验证
```

#### Office CLI 自动启用规则

| 任务 | 默认能力 |
|---|---|
| 读取 DOCX、XLSX、PPTX 结构 | Office 文档读取能力 |
| 修改 Word、Excel、PPT | Office 写入能力，需遵循项目权限 |
| 检查 Office 文件能否打开 | Office 验证能力 |
| PDF、Markdown、图片读取 | 文档读取能力，不默认调用 Office CLI |
| 知识库搜索和问答 | KB 只读能力 |
| 地图图层、空间分析 | GIS 能力 |
| 生成 Markdown 草稿 | 创作 Profile + 普通文件写入 |
| 生成 DOCX/PPTX/XLSX | 创作 Profile + Office 能力 |

#### Office CLI 的技术封装

Agent 不直接暴露任意 shell 形式的 Office CLI。建议由后端封装成逻辑能力：

```text
document_read
document_edit
document_generate
document_validate
document_export
```

底层才调用 Office CLI。这样后续替换 Office CLI、增加备用解析器或增加文件验证，不需要改变 Agent 和前端。

前端只显示：

```text
正在准备 Office 文档能力
已读取 Word 文档
正在验证 PPT 文件
Office 文件验证通过
```

高级 Run 详情可以显示实际使用的底层执行器，但普通用户不需要手动选择 Office CLI。

#### 创作 Profile

“创作模式”保留为 Agent Profile，主要配置：

- 输出目标：报告、Word、PPT、Excel、Markdown、地图成果。
- 默认模板。
- 默认成果目录。
- 是否允许 Office 能力自动启用。
- 是否必须经过格式验证。
- 是否需要用户确认后发布。
- 默认模型和 thinking level。

创作 Profile 不是一个新的对话内核，仍然使用同一个 Pi Agent Runtime 和 Run 系统。

## 3. 当前问题基线

本节不是新增需求，而是决定实施顺序的现状依据。

### 3.1 高优先级问题

| 编号 | 问题 | 影响 |
|---|---|---|
| P0-1 | Pi `cwd` 与自定义工具使用的当前工作区可能不一致 | Agent 可能读写错误目录，影响安全、产物和用户信任 |
| P0-2 | 当前工作区是进程级全局状态 | 多会话或项目切换时可能串写 |
| P0-3 | SessionManager 恢复前没有严格判断路径是否为具体 JSONL 文件 | 目录路径可能触发 `EISDIR`，恢复失败 |
| P0-4 | 工具流前端主要按最后一个工具块更新 | 交错事件或并发工具可能串卡片 |
| P0-5 | API Key 直接写入普通 JSON，非本机访问认证可选 | 凭据和文件 API 有安全风险 |
| P0-6 | Chat/Agent 主要依赖提示词和 UI 状态区分 | Chat 可能获得不应拥有的副作用工具 |
| P0-7 | 产物弹窗主要列当前目录文件，不严格读取 Run manifest | 无法确认文件是否由本次任务生成 |

### 3.2 中优先级问题

| 编号 | 问题 | 影响 |
|---|---|---|
| P1-1 | Run 绑定 HTTP 请求，服务重启后不能可靠恢复 | 长任务和失败恢复不稳定 |
| P1-2 | 任务中心主要是监控，没有完整控制动作 | 用户无法暂停、继续、重试或从失败点恢复 |
| P1-3 | 会话 fork 主要复制 JSONL，不是 Pi 原生分支 | 上下文、entry binding 和工作台关系可能不完整 |
| P1-4 | 记忆、知识库、会话和产物边界不够清晰 | 沉淀内容容易混乱或重复 |
| P1-5 | 模型、Provider、Key 和模式配置没有形成统一能力合同 | 选到不支持工具或图片的模型后才失败 |

### 3.3 前端维护问题

- `App.jsx` 承担过多全局编排状态。
- `ChatPanel.jsx` 同时承担 SSE、消息、Run、模型、队列和 UI 状态。
- `任务中心.jsx` 尚未成为真正的任务控制中心。
- `SettingsPanel.jsx`、`KnowledgeBase.jsx`、`SkillsManager.jsx` 和 `MemoryTab.jsx` 尚未围绕同一个项目对象组织。
- 需要运行验证 `DocViewer` 中 `showComments/setShowComments` 的静态风险。
- 需要修复 SSE 回调旧闭包、任务状态异常和项目切换后的状态同步问题。

## 4. 目标对象模型

第一阶段不要求立刻迁移所有 JSONL 数据，但新功能必须围绕下面的对象设计。

```text

type
status
rootPath
workspaceId
description
pinnedAt
archivedAt
memoryPolicy

defaultModelId

```

项目类型首批支持：

- 交通规划。
- GIS / 地图分析。
- 调研报告。
- Office 文档。
- 数据分析。
- 综合项目。

- 进行中。
- 待整理。

- 已归档。

## 5. 总体实施阶段

### 阶段 0：建立安全基线和验证入口

**目标**：在正式改造之前，保证不把当前工作树已有修改混入本次变更，并建立最小验证方式。

**修改内容**：

- 记录当前 Git 状态，不覆盖已有修改。
- 确认 `npm.cmd run verify` 的执行方式。
- 增加或整理 Agent 稳定性测试入口。
- 建立临时 `PI_AGENT_DIR` 测试目录的配置方式。
- 梳理当前 session、Run、workspace、memory 的实际文件位置。

**涉及文件**：

- `package.json`
- `server/agent.mjs`
- `server/workspace.mjs`
- `server/runs.mjs`
- `scripts/验证脚本.mjs`（如果现有脚本可以扩展）

**验收**：

- 能在不改变真实用户配置的情况下测试模型目录和 SessionManager。
- 能区分语法错误、构建错误、运行时错误和外部模型错误。
- 能记录每阶段验证结果。

### 阶段 1：统一项目、工作区和路径边界

**优先级：P0，必须先完成。**

#### 1.1 建立项目管理

涉及：

- `server/workspace.mjs`
- `server/index.mjs`
- `client/src/App.jsx`
- `client/src/components/SessionSidebar.jsx`
- `client/src/components/SettingsPanel.jsx`

必要时新增中文模块：

- `server/项目管理.mjs`

功能：

- 创建、读取、修改、归档项目。
- 项目类型和状态管理。
- 项目置顶和最近使用。
- 当前项目切换。
- 当前项目绑定工作区。
- 项目列表显示会话、任务、成果和待沉淀数量。

#### 1.2 统一工作目录

涉及：

- `server/workspace.mjs`
- `server/agent.mjs`
- `server/index.mjs`
- `server/kb.mjs`
- `server/office.mjs`
- `server/map.mjs`
- `server/runs.mjs`

功能：

- Pi 内置工具、officecli、KB、地图、memory 和 Run snapshot 使用同一个经过校验的工作区根目录。
- Run 开始时冻结 `workspaceSnapshot`。
- 用户切换项目不会改变正在运行的 Run 工作区。
- 所有路径统一经过一个解析函数。
- 统一处理 `..`、绝对路径、符号链接、外部文件根和读写权限。

#### 1.3 修复路径安全入口

重点检查：

- 地图导入路径。
- KB DOCX 导入路径。
- Memory 路径。
- Skill 导入路径。
- 文件上传、下载、删除、移动和导出路径。

**验收**：

- 两个项目同时运行不会互相写入。
- Pi `read/write/edit/bash` 与自定义工具使用同一项目根。
- 非法路径、符号链接越界和目录型 session path 都能被拒绝。
- 项目切换不会改变已有 Run 的工作区。

### 阶段 2：Agent 对话和运行稳定性

**优先级：P0，围绕现有对话流做内部增强。**

#### 2.1 稳定 Agent 状态机

涉及：

- `server/agent.mjs`
- `server/index.mjs`
- `server/runs.mjs`
- `client/src/components/ChatPanel.jsx`
- `client/src/components/任务中心.jsx`

功能：

- 明确 queued/running/waiting_user/cancelled/failed/completed 状态。
- 防止重复提交和重复启动。
- `ask_user` 期间保持原 Run 不变。
- abort 后不再接受旧 Run 的新工具调用。
- 任务结束时等待文件写入和快照完成。
- 失败时显示失败步骤和是否可重试。

#### 2.2 会话恢复

涉及：

- `server/agent.mjs`
- `server/index.mjs`
- `client/src/App.jsx`

功能：

- 恢复前检查路径存在且为具体文件。
- 检查 JSONL 文件可读和格式完整。
- 区分目录、缺失文件、损坏文件和有效文件。
- 恢复失败时仍可显示历史，但明确标记“不可继续运行”。
- 记录恢复错误，不静默吞掉异常。

#### 2.3 Pi Runtime 适配边界

初期可以保留在 `server/agent.mjs` 内部，后期再提取为中文命名模块：

- `server/Pi运行时管理.mjs`

建议接口：

```text
createSession
resumeSession
forkSession
prompt
steer
abort
compact
setModel
setThinkingLevel
listModels
refreshModels
listTools
reloadResources
dispose
```

前端和业务层不直接持有 Pi 原始 session 对象。

**验收**：

- 同一会话不能并行启动两个冲突 Run。
- 用户回答追问后，原 Run 能继续。
- 中止、失败、重试后状态不混乱。
- 页面刷新后能恢复会话状态。
- SessionManager 不再收到目录路径。

### 阶段 3：事件流稳定性增强

**优先级：P0，但不改变现有事件视觉表现。**

涉及：

- `server/agent.mjs`
- `server/index.mjs`
- `client/src/components/ChatPanel.jsx`
- `client/src/App.jsx`
- `client/src/api.js`

必要时新增：

- `server/事件记录.mjs`

#### 3.1 事件字段

现有事件名称继续保留，增加统一字段：

```text
protocolVersion
eventId
bootId
sequence
sessionId
threadId
runId
turnId
toolCallId
timestamp
replayable
payload
```

#### 3.2 前端事件投影

- 应用根部接收 SSE。
- `SessionStore` 保存会话消息和状态。
- `RunStore` 保存任务状态和事件。
- `ArtifactStore` 保存产物。
- ChatPanel 只订阅当前会话。
- 任务中心只订阅当前 Run。

#### 3.3 幂等和重连

- 按 `eventId` 去重。
- 按 `sequence` 排序。
- 按 `toolCallId` 更新工具块。
- SSE 重连时使用最后确认的序号。
- 服务重启后使用 `bootId` 区分旧事件和新事件。
- 对不可重放事件明确标记。

**验收**：

- SSE 断线后不会重复最终回答。
- 工具输出不会串到其他工具卡。
- 页面切换和组件重新挂载不会丢失后台 Run 状态。
- 事件、消息、Run 和文件变化可以互相定位。

---

### 阶段 4：Skills 稳定调用

**优先级：P0/P1，直接影响 Agent 能不能可靠工作。**

涉及：

- `server/agent.mjs`
- `server/index.mjs`
- `client/src/components/SkillsManager.jsx`
- `client/src/components/ChatPanel.jsx`
- `client/src/components/SettingsPanel.jsx`

必要时新增：

- `server/技能管理.mjs`

#### 4.1 Skill 预检

调用 Skill 前检查：

- Skill 是否存在。
- `SKILL.md` 是否可读取。
- 依赖脚本是否存在。
- 输入文件是否满足要求。
- 当前项目是否允许使用。
- Skill 是否允许写文件。
- 需要哪些工具、模型或外部依赖。

#### 4.2 Skill 执行状态

对话和 Run 中显示：

```text
发现 Skill
读取 Skill 说明
检查依赖
准备输入
执行中
执行完成
执行失败
```

#### 4.3 项目级 Skill 配置

每个项目设置：

- 默认 Skills。
- 允许 Skills。
- 禁用 Skills。
- Skill 版本或来源。
- Skill 的读写目录。

#### 4.4 Chat 与 Skill 的关系

Skills 页面中的 Chat 只用于搜索和推荐 Skill，不直接执行副作用操作。

流程：

```text
用户提问
  ↓
Skills Chat 搜索和推荐
  ↓
显示 Skill 说明、依赖和输入要求
  ↓
用户点击“使用此 Skill”
  ↓
创建 Agent Run
  ↓
执行前再次预检
```

**验收**：

- Skill 不存在时给出明确原因。
- 依赖缺失时不会让 Agent 假装执行成功。
- Agent 可以显示本次实际调用的 Skill。
- Skill 执行失败时能区分“找不到、读取失败、依赖失败、执行失败”。

#### 5.2 读取结果记录

- 文件类型和大小。

#### 5.4 读取缓存

- 文件未变则复用解析结果。

- 读取失败不会继续伪装成已读。

- 同名文件不会跨项目误读。

```text
activeWorkspaceMode =
  document | knowledge | skills | map | template | artifact
```

Chat 和 Agent 不是通过多个页面布尔值隐式切换，而是由当前资源和明确动作决定。

### 6.7 前端模式和页面行为

#### 顶层只保留 Chat 和 Agent

前端不再同时显示“Chat、Agent、Office CLI、创作”四个并列按钮，避免用户不知道应该选择哪一个。

```text
顶层模式：Chat | Agent

当 mode = Chat：
  当前页面决定 Chat 的上下文：知识库 / Skills / 文件资料

当 mode = Agent：
  profile 决定执行方式：创作 / Office / Research / GIS / Data
```

#### 知识库 Chat

知识库打开时，右侧默认显示只读 Chat：

- 只能搜索知识库和读取用户指定文件。
- 回答必须显示来源。
- 支持引用定位。
- 可以保存为研究笔记。
- 可以生成待沉淀记忆。
- 可以点击“交给 Agent 处理”，转为 Agent Run。

#### Skills Chat

Skills 页面打开时，右侧默认显示 Skill 搜索 Chat：

- 根据自然语言查找 Skill。
- 解释 Skill 的用途和限制。
- 检查依赖和输入文件。
- 推荐适合当前项目的 Skill。
- 点击“使用此 Skill”后进入 Agent Run。

Skills Chat 不直接执行写文件、bash 或 Office 修改。

#### Agent 工作台

Agent 在项目工作台中运行，右侧顶部显示：

```text
当前项目 / 当前工作区 / Agent Profile / 模型 / 权限模式 / Run 状态
```

Agent Profile 选择器替代原来的“Office CLI 模式”和“创作模式”按钮。

例如：

- 选择“创作 Profile”后，任务可以生成报告、Markdown、Word、PPT 或 Excel。
- 选择“Office Profile”后，任务优先处理已有 Office 文档。
- 选择“Research Profile”后，任务优先读取资料、知识库和引用来源。
- 选择“GIS Profile”后，任务可使用地图和空间分析能力。

#### Office CLI 不作为前端模式

前端不提供“调用 Office CLI”开关。用户只需要说明任务，系统根据以下信息自动判断：

- 输入文件后缀。
- 用户要求的动作是读取、修改、生成还是验证。
- 输出文件格式。
- 当前 Agent Profile。
- 当前项目允许的工具。
- 当前文件是否正在被其他 Run 使用。

判断结果显示为能力状态，而不是命令行细节：

```text
正在准备 Office 文档能力
正在读取 Excel 工作表
正在验证生成的 PPT
Office 文件验证通过
```

#### 原有状态迁移

当前 ChatPanel 中的 `editMode = office / agent` 不直接继续扩展。计划改为：

```text
mode = chat | agent
profileId = creative | office | research | gis | data | general
capabilityPlan = office | kb | map | file | mixed
```

这样“创作”是 Agent Profile，“Office CLI”是底层执行能力，二者不再和 Chat/Agent 混在一层。

### 6.8 多会话、历史和任务中心行为

#### 新建对话

用户在对话 A 中点击“新建对话”时：

```text
创建会话 B
  → 会话 A 保持原 Run 状态
  → 会话 A 继续在后台运行
  → 会话 B 成为空闲会话
  → 左侧同时显示 A 和 B
```

新建对话不能调用 abort，也不能清空当前项目的后台任务。

#### 切换对话

切换会话只改变当前显示对象：

- 不停止原会话。
- 不重新启动原 Run。
- 恢复原会话的消息、工具状态和待回答问题。
- 显示原会话的未读事件。
- 可以从任务中心再次定位回该会话。

#### 历史记录

历史不以“是否已经生成文件”为显示条件。以下会话都必须显示：

- 新建但未完成的会话。
- 正在运行的会话。
- 等待用户回答的会话。
- 失败待处理的会话。
- 只有 Chat 问答的会话。
- 已生成成果的会话。
- 已归档的会话。

每条历史显示：

```text
标题 / 最后一条消息 / 所属项目 / Chat或Agent / 状态
最近活动时间 / 未读数量 / Run数量 / 产物数量 / 是否固定
```

#### 任务中心

任务中心显示当前项目的全部 Run，并按以下区域分类：

```text
正在运行
等待用户
排队中
失败待处理
最近完成
```

点击任务后：

1. 打开对应会话。
2. 定位到对应 Run。
3. 展开任务时间线。
4. 显示工具、文件变化、产物和验证结果。

任务中心提供：

- 取消。
- 继续。
- 重试。
- 复制为新任务。
- 查看产物。
- 查看差异。
- 回滚。

#### 并行限制

- 同一个会话同时只能有一个运行中的 Run。
- 不同会话允许并行。
- 默认全局最多两个 Agent Run。
- 超过限制的任务排队。
- 只读 Chat 可以并行检索。
- 修改同一文件或同一成果目录时必须加锁或等待。

#### 前端状态组织

第一阶段不强制引入新的状态管理框架，但 App 层必须维护按会话索引的状态：

```text
sessions[sessionId] = {
  messages,
  run,
  unreadCount,
  pendingQuestion,
  draft,
  connection,
  error
}
```

ChatPanel 只读取当前 sessionId；任务中心读取 runId；项目侧栏读取 projectId。三者不能再互相依赖组件是否挂载。

## 9. 系统影响关系

### 9.1 项目切换

```text
用户选择项目
  → App 更新 projectId
  → 加载项目工作区、会话、成果、记忆和 Skill 配置
  → 新建或恢复会话时绑定 projectId/workspaceId
  → Run 创建时冻结 workspaceSnapshot
  → SSE 事件带 projectId/runId
  → 前端 Store 更新对应项目和 Run
```

项目切换不能修改已经运行的 Run 的工作区。

### 9.2 Agent 生成产物

```text
用户发送任务
  → Agent Profile 检查工具和路径
  → 创建 Run
  → 记录 before snapshot
  → 工具执行并产生事件
  → 写入临时文件
  → 文件格式和内容验证
  → 生成 Artifact manifest
  → 完成 after snapshot
  → 任务中心显示成果
  → 用户发布或继续修改
```

### 9.3 记忆沉淀

```text
Run 完成
  → Agent 生成候选记忆
  → 保存 proposed 状态
  → 前端显示待沉淀卡片
  → 用户批准/编辑/拒绝/合并
  → 写入项目 memory
  → 后续 context 注入 approved 记忆
```

## 10. 错误传播和状态风险

### 10.1 Agent 调用失败

```text
Pi 或工具失败
  → AgentManager 标记当前 turn/run 失败
  → 记录错误类型和失败步骤
  → 判断是否有副作用
  → 允许安全重试或要求用户处理
  → SSE 发出 agent_error/run_finished
  → 任务中心显示失败原因
```

不得在工具已经产生副作用后，未经判断直接重放整轮请求。

### 10.2 文件生成失败

```text
写入失败或验证失败
  → 保留临时文件或清理半成品
  → Artifact 标记 verification_failed
  → Run 标记 failed 或 completed_with_warning
  → 不发布为正式成果
  → 向用户显示重试和清理选项
```

### 10.3 前端断线

```text
SSE 断开
  → 记录最后确认 sequence
  → 自动重连
  → 按 eventId 去重
  → 按 sequence 补事件
  → 重新投影 Session/Run/Artifact 状态
```

### 10.4 记忆写入失败

```text
用户批准记忆
  → 写入失败
  → 保留 proposed 状态
  → 显示失败原因
  → 不从待沉淀列表删除
```

## 11. 测试和验收计划

### 11.1 Agent 对话稳定性

- 普通 Chat 能完成问答并显示来源。
- Agent 调用多个工具时工具卡不串位。
- 重复点击发送不会创建重复 Run。
- `ask_user` 后刷新页面仍能继续。
- abort 后旧 Run 不再继续调用工具。
- Pi 忙碌时不会出现多个并发执行。
- 模型错误、工具错误和路径错误显示不同原因。

### 11.2 Skills 稳定性

- Skill 存在并成功读取。
- Skill 不存在时明确提示。
- Skill 依赖缺失时禁止假装完成。
- 项目禁用的 Skill 无法执行。
- Skills Chat 推荐 Skill 后，必须通过明确按钮进入 Agent Run。
- Run 详情能显示实际使用的 Skill。

### 11.3 文档读取稳定性

- Markdown、DOCX、XLSX、PPTX、PDF 和图片分别测试。
- 目录路径、缺失路径和损坏文件分别测试。
- 大文档截断有提示。
- 同名文件跨项目不会误读。
- 文件变更后缓存失效并重新解析。
- 知识库 Chat 答案显示来源。

### 11.4 产物稳定性

- 文件先写临时路径，再验证后发布。
- Word、Excel、PPT 生成后可以重新打开。
- 产物能反查 Run、会话、项目和模型。
- 文件覆盖前有明确策略。
- 验证失败的文件不会被标记为正式成果。
- 回滚后生成新的审计记录。

### 11.5 项目和记忆

- 项目分类、状态、置顶和归档可用。
- 项目切换不影响正在运行的 Run。
- 项目记忆只接受批准后的内容。
- 项目列表显示待沉淀数量。
- 会话、知识库、记忆和成果分开显示。
- 固定会话后刷新页面仍能恢复。

### 11.6 安全和边界

- Chat 不能写文件或执行 bash。
- 非法路径和符号链接越界被拒绝。
- 非 loopback 访问要求认证。
- session/run/rollback 进行所有权校验。
- API Key 不直接暴露给前端。
- 未审批的 memory_update、外部根和高风险工具不能执行。

### 11.7 质量门槛

每个阶段必须完成：

- `npm.cmd run verify`。
- 相关接口的最小 smoke test。
- 关键页面手工回归。
- 失败场景验证。
- 说明哪些依赖真实模型、哪些可以离线验证。

静态检查通过不能代替 Office 文档打开验证、浏览器交互验证和真实 Agent Run 验证。

## 22. 第四阶段本次实现记录

本次在分支 `codex/规聚项目稳定性第三阶段` 继续实施第四阶段 Harness 控制能力，重点解决“切换会话后后台任务不可见、服务重启后 Run 假装仍在执行、任务失败后没有明确恢复入口”三个稳定性问题。保留工作树中原有未提交修改，未执行 reset 或覆盖操作。

已完成：

- 新增根级持久事件 Store `server/事件存储.mjs`，将重要 Run、Agent、工具、产物和恢复事件追加写入 `.oaw/events/事件流.jsonl`；高频 token、thinking 和 tool_output 仍走当前对话 SSE，避免持久日志失控。
- 新增跨会话事件接口 `/api/agent/events`，支持按 `clientId`、`threadId`、序号和 `Last-Event-ID` 重放；前端 App 级订阅不依赖当前 ChatPanel 是否挂载。
- 增加事件状态和阅读游标接口 `/api/agent/events/state`、`/api/agent/events/read`，前端按客户端游标避免刷新或重连后重复提醒。

- 新增任务中心控制接口和 UI：`POST /api/runs/:id/cancel`、`POST /api/runs/:id/resume`、`POST /api/runs/:id/retry`。取消先写入 `cancel_requested`，随后中断 Pi；恢复/重试创建新的 Run，并记录 `recoveryOf`、`recoveryAction` 和来源 Run。
- 恢复/重试前重新执行工作区、引用、Skills / 工作流和 Office CLI 预检，尽量复用 Pi JSONL 会话；继续后仍经过文件变更扫描和产物校验，再完成新的 Run。
