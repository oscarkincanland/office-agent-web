# 规聚启动体验、Agent 交互与动效完整修改计划

## 1. 结论与边界

先让系统**可理解、可信、可恢复**，再让它更有动感。当前界面已具备运行状态呼吸、流式文字、跑马灯、进度与按钮反馈，不宜再增加大面积持续动画。新增动效应只回答三个问题：**我做的操作生效了吗？Agent 正在做什么？接下来需要我做什么？**

本计划合并三轮审查：启动/生产力与缺陷、Agent 人机交互、动效与微交互。它是[网页端与桌面端协同演进完整计划](2026-09-20-001-规聚网页端与桌面端协同演进完整计划.md)的体验子计划，**不替代 Electron 架构与内置浏览器重构计划**。本轮只制定方案，不修改功能代码，也不把现有缺陷视为已修复。

实施原则：网页端先跑通同一套状态语义和交互规范；未来 Electron 桌面壳复用 React 组件、动效变量、Agent 事件语义与验收用例。系统原生窗口、通知、浏览器视图另做平台适配，不在本计划里平行复制一套界面。

## 2. 当前基线与证据

2026-09-23 复核代码为 `v0.11.10`、HEAD `d913b183`；本地已有未提交的 `client/src/App.jsx` 和浙江地图配置变动，属于用户工作，实施者不得覆盖。旧双端计划写于 `v0.11.2`，其具体数字需以实施日重新测量。

| 领域 | 已观察到的现状 | 影响与计划入口 |

当前内置浏览器中可见的首屏也验证了“左项目栏 + 中央对话 + 右预览”在常规宽度下会压缩核心任务空间，并显示了 Work 与“自动批准”的强状态。浏览器截图在本轮只做现场观察，未形成可复查的截图档案；正式视觉结论与不同宽度、不同状态的判断要在 P0 留存同一版本截图后复核。尚未执行真实模型、Office 操作或完整端到端测试。

## 3. 产品目标与可量化成功标准

1. 首次打开/刷新后，用户在 **5 秒内**能看见明确状态：可用、正在加载、部分功能不可用或失败可重试；不得用空列表冒充成功。此处 5 秒是**呈现状态**目标，不是承诺所有远端资源 5 秒完成。
2. 发送前用户能读到当前 **模式、目标工作区/文件、会触发的能力边界**；Agent 正在等待用户时有唯一明确的操作入口。
3. 每个运行都能区分 `运行中 / 等待批准 / 已完成且已验证 / 已完成但未验证 / 部分失败 / 失败 / 已取消`；任务中心、对话摘要、成果面板一致。
4. 持续运动不承载唯一状态信息；系统设置“减少动态效果”及产品“关闭动效”下仍可完成所有任务、看到所有关键状态。
5. 在基线设备和测试浏览器上，交互后的主要反馈可感知且不妨碍输入；以实际测量确定启动时间、主线程长任务、帧率与内存阈值，不能先写漂亮但未验证的性能数字。
6. 网页端上线前通过自动化回归、键盘/读屏抽查和真实 Agent 任务走查；桌面端引入时重用同一用例，并额外验证系统设置、窗口焦点和原生通知。

## 4. 交互与动效规范

### 4.1 设计规则

- **状态先于动画**：失败不能闪绿色勾；队列中不能显示“正在写入”；完成动效必须由权威运行状态触发，不能按固定计时猜测。
- **一次性优于循环**：点击、展开、完成反馈尽量一次完成；持续循环仅用于真正运行且持续可见的少量位置。多个列表项同时运行时优先静态标签或低频指示。
- **文字永远可读**：运行中的会话名先保证省略号、悬停完整标题/键盘可读；滚动只在溢出且需要阅读时发生。不可因流光背景使文字消失。
- **不移动用户的目标**：审批按钮、输入框、正在阅读的结果不因进度事件上下跳动；新消息到来时只在用户处于底部且未主动上滚时跟随。
- **不奖励危险操作**：全局自动批准、永久放行不做“成功庆祝”动画；权限扩大必须用明确文案和可撤销入口。
- **跨端同语义**：Web 和 Electron 的状态、文案、时序一致；平台差异只体现在原生控件/窗口能力。

### 4.2 建议保留、新增与收敛的动效

| 场景 | 建议动效/互动 | 静态与无障碍回退 | 优先级 |
| --- | --- | --- | --- |
| 首屏加载 | 三段式状态：加载项目/会话 → 恢复上次任务 → 可输入；只对实际未就绪区域显示稳定骨架，不做全屏反复闪烁 | 文字状态、错误和“重试”始终可见；不得把请求失败当成空工作区 | P1 |
| 发送消息 | 发送按钮按下反馈，消息从“待发送/排队”变为“已接收”；失败时保留草稿和重试 | 状态文字/图标等价；不能靠纯颜色或动画提示 | P2 |
| Agent 执行 | 顶部压缩为“当前阶段 + 上次完成步骤 + 等待动作”；阶段切换轻微渐变，运行点低频或静态 | `role=status`/`aria-live` 只播报有意义的阶段，避免每个 token 报读 | P2 |
| 工具审批 | 待批准卡片一次性高亮并把焦点引到卡片标题或首个安全动作；批准后原位显示决定与影响范围 | 不抖动、不持续脉冲；“总是允许”明确范围、有效期与撤销位置 | P1/P2 |
| 文件/成果变化 | 文件树的被改文件轻微短时高亮；预览停在用户位置，提供“查看差异”；正式成果状态轻微揭示 | 文本列出变更文件、验证证据、可回滚性；不自动抢焦点 | P2/P3 |
| 运行结束 | 结果卡一次性淡入；已验证为勾，部分失败/未验证用各自标识和说明 | 不用烟花、彩纸、误导性成功音效；状态来自事件/验证结果 | P2 |
| 面板/命令入口 | 右预览、任务中心、命令面板以短位移+透明度出现，关闭后焦点返回触发控件 | 无动效时直接切换；窄屏避免整页滑出导致内容错位 | P3 |
| 模型/模式切换 | 选中状态即时变化，异步保存另显“保存中/失败”；模式变化预告能力与权限 | 不用转盘隐藏保存失败；键盘切换后焦点稳定 | P2 |
| 跑马灯 | 收敛默认的连续流光/呼吸，保留可选个性化；修复滚动与样式叠加冲突 | 关闭/减少动效时静态文字、完整标题和状态色标 | P3 |

动效时间先作为设计试验值：按钮反馈约 **80–150 ms**，菜单/卡片 **150–220 ms**，面板 **180–280 ms**；不以等待动画结束延迟真实结果。优先动画 `opacity`、`transform`，避免对大量列表项反复动画化 `width/height/background-position`。这些不是验收硬编码值，须在 P3 用实际录屏、帧时间和用户走查微调。流式文字可直接显示或按用户偏好逐帧显示，但真实完成后不应继续“演”很久。

### 4.3 完整与克制档位的建议

- 默认改为“克制”须先经小范围试用验证；在此之前至少保证“关闭动效”全覆盖，避免未经测试改变用户已选设置。
- 系统 `prefers-reduced-motion: reduce` 优先级高于产品“完整动效”；产品“关闭动效”优先级高于每个局部样式。状态、进度、错误都保留静态等价信息。
- 集中管理少量动效变量与状态样式，不为每个组件再创建独立设置。对会话侧栏、任务中心、对话流、地图等已有动画逐项清点，避免一个 CSS 全局规则误杀地图操作的必要过渡。

## 5. 分阶段实施（网页端和桌面端同步口径）

阶段按门槛推进；估时是单名熟悉项目的开发者配合设计/测试的粗估，不代表发布承诺。P0 可与设计规范准备并行，P1–P2 的安全/状态问题不能被 P3 的视觉工作抢先替代。

### P0：冻结可复现基线与体验证据（约 2–3 天）

- [ ] 记录提交、未提交变动和环境；建立独立测试数据，不改现有用户会话/权限。保留当前 `App.jsx` 与地图配置的用户修改。
- [ ] 在同一版本留存新用户、老会话、失败恢复、Agent 运行、待审批、成果页截图/短录屏；覆盖常规桌面宽度、窄窗口、200% 缩放，以及亮/暗主题。截图中的敏感路径与数据先脱敏。
- [ ] 测量首屏请求、会话数量/响应体积、轮询频率、帧时间、主要布局宽度；明确问题复现步骤与性能基线。
- [ ] 修复/更新已过时的回归断言：`scripts/对话流性能回归测试.mjs:25` 仍在 `ChatPanel.jsx` 查找已迁至 `事件展示.js` 的常量。先保证测试能表达真实契约，不把测试错误当产品 bug。
- [ ] 核对现有 `npm.cmd run verify`、浏览器/审批/任务相关测试的通过情况；失败逐项记录原因。同步旧双端主计划的版本基线引用，避免以 `v0.11.2` 的规模数据当今天事实。

**出口**：每个高优先问题有复现、截图或代码证据及负责人；干净可重跑的基线测试清单出炉。桌面端本阶段只对齐设计与事件契约，不启动大规模 UI 重写。

### P1：先修可信度和阻断性缺陷（约 4–7 天）

- [ ] 启动请求明确 `loading/ready/partial/error`；失败有重试与保留上次可用数据策略。`refreshFiles/refreshSessions/refreshProjects/listWorkspaces` 不再静默伪装空结果。
- [ ] 修复会话恢复时序；会话列表晚到、工作区缺失、已删会话、恢复接口失败分别显示正确状态。历史内容与可继续执行能力分开表示。
- [ ] 修复任务中心非整页入口不可见；任务中心的“运行结束、任务达成、步骤成功数、验证结果”不得混成一个“已完成”。
- [ ] 对齐审批真实作用域：自动批准/永久规则要说明是否跨会话、跨项目、是否持久、如何撤销；默认安全性和既有规则迁移需单独评审，不得只改按钮文案。
- [ ] 成果面板“可回滚”文案由实际 `rollbackTarget` 等能力生成；不可回滚时不暗示可回滚。

**出口**：断网/500/空列表/慢响应/恢复失败均可解释且可重试；审批与成果文案不超出真实能力；完整自动化用例及一次真实历史会话走查通过。桌面端共用状态枚举和审批语义，不做仅网页端有效的临时提示。

### P2：重排 Agent 主任务流（约 5–8 天）

- [ ] 以“选工作区/目标 → 选 Chat/Work/Review → 输入任务 → 确认影响范围 → 观察执行 → 验收成果”为主路径，空白态按模式给可执行示例，不直接引导只读模式去改文件。
- [ ] 在输入区显示可移除的“当前目标文件/工作区”上下文标签；若仅是参考文件，明确不等于授权写入。发送前可检查目标，尤其是多个打开文档时。
- [ ] 模型选择收敛为当前、最近、收藏和全部搜索；能力标签按真实模型元数据计算，不能仅凭名称猜“文本/视觉”。保留完整列表的高级入口。
- [ ] 运行态只展示当前关键步骤与下一步，详细事件留可展开轨迹；待用户审批时从任务中心、当前会话、全局未读入口均能定位到同一动作。
- [ ] 任务结果卡统一展示目标是否达成、改了哪些文件、验证做了什么、尚未验证/失败项、下一步。原始错误 JSON 在“技术详情”里，普通用户先见可操作解释。
- [ ] 命令面板结果改为可键盘操作的语义控件，支持焦点圈、上下键、Esc 关闭与关闭后焦点归还；首屏/窄屏优先保证输入区与结果区空间。

**出口**：新用户能在无引导下完成一次只读问答和一次有批准的文件任务；找得到运行、审批和成果；无“已完成但实际步骤失败”的误解。Web 先交付，Electron 接入时用同一组件与接口适配。

### P3：动效治理与微交互落地（约 4–6 天）

- [ ] 为每类动效建“触发条件、持续时间、可中断性、静态回退、屏幕阅读器播报”表；只保留对主任务有意义的动画。
- [ ] 修复跑马灯滚动与流光/霓虹互相覆盖的问题，给短名/长名、多样式、侧栏收起/展开、字体晚到写组合测试。测量环节防抖或减少额外定时器，避免大量会话时不必要的布局工作。
- [ ] 系统减少动效与产品关闭档覆盖全局旋转、blink/pulse、扫描线、流式揭示及弹层入场；检查浏览器、地图等独立模块的状态提示仍可理解。
- [ ] 按第 4 节为发送、阶段变化、审批、文件改动、结果、面板设计一次性反馈；所有动效都由真实状态驱动，可中断、不会阻塞点击/输入/焦点。
- [ ] 为快速连续事件、断线重连、历史回放设计“合并播报/立即落定”，避免进度卡反复跳动、文字重新打字或旧动画覆盖新状态。

**出口**：跑马灯组合和减少动效测试通过；连续 10 分钟运行无持续闪烁干扰；100+ 会话列表、长任务日志下没有明显掉帧或阅读位置跳动。桌面端增加系统动效偏好与 React 状态同步验证。

### P4：跨端体验、可访问性与性能验收（约 3–5 天）

- [ ] 用网页端主流 Chromium/Edge 与窄窗口验证三栏折叠、缩放、键盘操作、焦点归还、读屏状态、对比度与最小点击目标；不凭截图宣布 WCAG 合规。
- [ ] 运行五条跨层回归：首次启动部分失败、会话恢复失败、并行任务等待审批、工具部分失败仍结束、成果不可回滚。每条要同时核对 API/SSE、React 状态、文案和动画。
- [ ] 测量优化前后首屏可交互时间、长任务期间主线程长任务数/帧时间、会话轮询流量；若改动退化，优先撤销装饰性动效。
- [ ] `npm.cmd run verify`、针对性单测/集成测试、真实模型与 Office 小样本走查分别记录，不以构建通过代替真实交互验收。
- [ ] 将共享状态与动效规范进入桌面端验收清单：窗口失焦/恢复、系统减少动效、原生通知与应用内状态同步、窗口尺寸、WebContentsView 与 React 焦点交接。若桌面壳尚不存在，记为“待桌面阶段验证”，不虚报双端通过。

**出口**：P0 基线指标无实质退化，关键任务成功率和理解度通过走查，回归矩阵有证据；文档、变更日志与双端主计划的进度同步更新。

## 6. 系统影响与测试矩阵

主链路：**用户操作 → React 输入/状态 → HTTP/SSE（桌面未来为 IPC）→ Agent/审批/会话服务 → Run/成果持久化 → 事件回推 → 对话/任务中心/预览**。动效只订阅被确认的 UI 状态，不得自行推断服务端成功。

| 情况 | 期待行为 | 重点测试层 |
| --- | --- | --- |
| 启动一个接口失败，其他成功 | 仍能使用已就绪功能，失败模块提示重试；不清空有效缓存 | API mock + 浏览器视觉 |
| 保存过的会话比列表晚到 | 恢复一次且定位正确，不产生空 Agent 会话 | React 状态 + 会话接口 |
| 历史可读但 Agent 恢复失败 | 显示“只读历史/恢复失败”，不能假装可继续原线程 | 服务端返回 + 浏览器交互 |
| 自动批准与永久规则 | 明确作用域、撤销路径；显式 deny 仍拒绝 | 审批策略 + UI 文案 |
| 并行 Run 部分步骤失败 | 顶层结果不显示为“全部成功”，可查看失败步骤与未验证项 | SSE 事件 + 任务中心 + 结果卡 |
| 持续事件突发/断线回放 | 不重播长动画、不重复输出、不抢滚动/焦点 | SSE 回放 + 性能 |
| 系统减少动效/产品关闭档 | 无连续运动；状态和操作不丢失 | CSS/JS + 键盘/读屏 |
| 窄屏打开预览/任务中心 | 主输入区可用，面板可关闭，焦点归还 | 响应式 + 视觉走查 |

非功能边界：审批规则的作用域改变属于安全与数据迁移，必须配服务端测试和回滚；“最近/收藏模型”仅存轻量本地偏好，不复制密钥或凭据；任何可回滚性声明以服务端能力为准。会话列表与任务中心的轮询/事件频率需按实际负载压测，不能用动画掩盖数据延迟。

## 7. 发布、回滚与资源

- 每阶段一个可回退的变更批次；先改状态与文案，再改布局，最后开启动效。若实验性动效有性能/可访问性回归，优先关闭该动效，不回退已验证的错误处理。
- 引入新审批作用域或持久化格式时，保留旧配置读取与迁移回退，发布前提示现有用户检查“自动批准”状态；不能静默扩大授权。
- 最低协作：1 名熟悉 React/Node 的开发者、1 名能做任务走查的产品/设计参与者、1 名安全/测试复核者（可兼职）。总历时粗估 **4–6 周**，取决于 P1 审批语义和真实环境验证；桌面端壳体建设仍按双端主计划推进。
- 每阶段汇报：已修问题、未修问题、测试证据、性能变化、网页端与桌面端分别达到的门槛。视觉截图与真实模型验收需在可复查环境留档。

## 8. 不做的事与风险

- 不把“多做动画”当成优化目标；不做全屏开场、打字机等待、每个工具调用弹窗、无限彩色跑马、完成撒花。它们会损害阅读和速度。
- 不在这份计划里迁移 Electron 主进程、重写内置浏览器或重建设计系统；遵从双端主计划的共享核心和阶段验收。
- 不让前端根据“没有报错”推断任务成功；最终状态必须和 Run/验证证据一致。
- P0 之前不承诺精确性能收益或 WCAG 合规；本轮现场截图未归档，视觉审计还需按统一视口和状态补证据。

## 9. 实施顺序摘要

`P0 证据和测试基线 → P1 启动/恢复/审批可信度 → P2 Agent 主任务流 → P3 动效治理 → P4 双端验收`。

优先级若被迫压缩：必须先完成 **P1 + P2 中的任务结果与目标可见性**；P3 只保留修复跑马灯冲突、减少动效全覆盖与关键状态反馈，其余装饰性微交互延后。
