# 规聚任务结论、事件流、对话层级与工具图标完整修改计划

## 一、定位与交付边界

本计划供其他 Agent 分阶段实施，**本次只规划，不改功能代码**。它接续[启动交互与动效计划](2026-09-23-001-规聚启动交互与动效完整修改计划.md)及其[实施记录](2026-09-23-001-实施记录.md)：P1–P4 的主要代码和自动化用例已提交，但真实浏览器、真实模型、长时运行验收仍未完成。这里不重做启动骨架、跑马灯、命令面板和动效闸门，而是补齐四个相互依赖的缺口：

1. Pi SDK 回合结束、Run 结束、任务达成、产物验收的**终态契约**。
2. 最终回复的**唯一归属、去重、断线重放与跨 Run 隔离**。
3. 面向用户的**对话层级**：结论优先，思考与工具细节按需展开。
4. 工具调用的**语义图标**：工具类别与执行状态分别表达。

网页端先实现共享数据契约与组件；未来 Electron 复用这些语义和组件，IPC 只做传输适配。不要为了桌面端复制一套状态判断。安全审批、模型供应商、内置浏览器重构不在本计划范围；不得修改默认权限、既有会话和凭据。

## 二、当前证据与不可混淆的事实

基线按 2026-09-24 的 `dfd0011d` 复核；实施者开始前须重新查看 `git status` 和 HEAD。当前另有两份用户未提交的浙江地图配置，**保留原样**。本轮 `verify`、主任务流、动效、无障碍、任务中心、性能预算通过；跨层回归第一次因临时服务启动超时失败，单独重跑通过。因此“自动回归通过”不等于真实浏览器/模型已经验收。

| 现状证据 | 风险/目标 |
| --- | --- |
| `server/agent.mjs` 的 `agent_settled` 发 `assistant_final`、`agent_end`；缺少 `complete_task` 时还可能追加收尾提醒回合 | Pi 的一个回合结束不是整个 Run 结束；提醒回合不得生成第二份用户终稿 |
| `server/agent.mjs` 把 `assistant_final` 记入 Run；`server/index.mjs` 多条收尾路径又手动 `recordRunEvent("assistant_final")` | Run 存储可重复，重放与断线兜底易出现双终稿 |
| `_promptEntry` 重置 `pendingCompletion`，但未同时重置 `lastFinalText` | 新 Run 可能误取上一轮的权威文本；要按 Run 身份隔离 |
| `complete_task` 的声明、`finishRun` 的实际状态、验证结果分别产生 | “模型声明成功”不能压过实际失败、取消或验收失败 |
| `client/src/事件展示.js` 的 `flowEventTone()` 对所有 `run_finished` 返回 `success` | 失败/取消的执行流仍可能显示成功色 |
| `ThinkingBlock` 默认 `expanded=true`；`ToolCard` 只有加载/勾/叉状态图标 | 结论被过程挤压，用户难以快速辨认正在用什么能力 |

实施前把上表逐项复现为测试，不以本计划的行号作为永久定位依据；代码可能继续演进。

## 三、共享产品契约（先定，后编码）

### 3.1 四层状态，分开存储与展示

| 层 | 唯一问题 | 权威来源 | UI 文案原则 |
| --- | --- | --- | --- |
| Pi 回合 | 模型当前推理回合是否结束？ | Pi `agent_settled` / SDK 事件 | 内部轨迹；不直接写“任务完成” |
| Run 生命周期 | 本次运行是否仍在执行、等待、取消或已终结？ | Run Store 的状态与 `run_finished` | “运行结束/失败/已取消”，不可偷换成目标达成 |
| 任务达成 | 用户目标成功、部分完成、受阻还是失败？ | `complete_task` 显式声明，缺失时保守推断；需与客观结果一致 | 显示“模型声明”或“系统推断”的来源；部分完成列未完成项 |
| 成果验收 | 文件、操作和交付物实际检查到什么程度？ | 校验/发布/成果记录 | 已验证、验证失败、未验证分别表达；不得用绿色勾替代证据 |

优先级：取消/运行失败/写入或发布失败/验收失败等客观结果可**下调**声明结论；模型的 `complete_task: success` 不可**上调**客观失败。`run_finished` 一旦发出，该 Run 的终态为单调不可回退；迟到事件只能补充诊断，不得把失败改成功。`agent_end` 不等于 `run_finished`。`partial` 和 `blocked` 不能用 success 色。缺少证据时显示“未验证”，不伪造成功。

### 3.2 最终回复的唯一归属

每个 `runId` 至多一个用户可见的权威最终回复，允许流式草稿在同一气泡内被最终全文修正；最终回复与结果卡是两种互补信息，不能重复整段文案。服务端应确定一个权威写入点（例如 Run 收尾归档），其余通路只发送引用/兜底，不重复追加相同事件。每个终稿携带 `runId`、稳定 `messageId` 或等效幂等键、版本/序号和来源。客户端用这些字段处理 SSE 实时、断线重放、历史加载与 `run_finished.finalText` 兜底；文本相同不是唯一去重依据，因为用户可能连续提出相同问题。

新 Run 创建时清理上一 Run 的终稿缓存及临时流式缓冲，完成声明也必须绑定 `runId`。旧 Run 迟到事件不能补写当前 Run。错误、取消、收尾提醒、再次 settle 需走同一幂等路径。不得为了去重丢失失败前已生成的有效正文。

### 3.3 对话主视觉层级

默认主轴：用户目标/提问 → Agent 最终回答或可操作状态 → 结果卡（达成、变更、验证、未完成、下一步）。“思考”“工具调用”“原始事件”是可展开的证据层，默认收起；运行中只显示阶段、当前工具类别和需要用户行动的一项。思考内容不作为唯一进度来源，也不得被当成结论。用户手动展开后保持本 Run 内状态；切换历史会话时按产品约定重置，不突然抢滚动或焦点。`aria-expanded`、按钮语义、键盘 Enter/Space 与焦点可见必须齐备；长思考/长工具输出不应阻塞长列表渲染。

### 3.4 图标语义与资源

先沿用现有 `Icon.jsx` 的线框风格和尺寸体系，不以引入整套新库为前提。推荐优先评估 [Lucide](https://lucide.dev/icons/) 的 React 图标（含 `brain`，ISC 许可；正式引入前复核所用版本的许可证与打包大小）；备选 [Phosphor](https://phosphoricons.com/)（MIT，需确认视觉一致性）。若增加依赖，只按需导入、检查 tree-shaking 与 bundle 预算；也可在现有 Icon 中增补少量经过授权的 SVG。

图标两层并列：**语义图标**表示能力（脑/搜索/文件读取/编辑/终端/浏览器/Office/知识库/审批/通用工具）；**状态图标**表示运行中/成功/失败/待审批，保留现有勾、叉、加载语义。映射集中在单一表，由 `tool.name`/规范化事件类型决定；未知插件一律用通用工具图标 + 可读名称。不得根据工具输入的自然语言猜类别，不得把脑图标当作“任务成功”；颜色之外保留文案和无障碍名称。图标本身可 `aria-hidden`，整行提供组合可访问名。

## 四、分阶段实施与 Agent 分工

遵循“契约 → 服务端 → 前端 → 图标 → 真实验收”的依赖。最多四个并行工作流，避免多个 Agent 同改 `ChatPanel.jsx` 或终态收尾路径。建议按模块交接、每阶段合并后跑基线回归。

### P0 契约与失败样本（建议 1–2 天；负责人：协议/测试 Agent）

- 列出 Pi SDK `agent_settled`、`complete_task`、`assistant_final`、`agent_end`、`run_finished` 的时序与 Run Store 写入位置；画出正常、缺声明提醒、失败、取消、重连五条路径。
- 定义 Run 终态枚举、completion 来源、verification 来源、终稿幂等键；补版本兼容策略（旧事件缺字段时保守展示）。
- 写失败先行测试：同 Run 两次 settle、跨 Run 旧终稿、模型声明成功但产物验收失败、取消后迟到成功、重复 SSE、部分成功。
- 记录基线 `verify`、现有 `test:sse-protocol`、`test:run-trace`、`test:chat-flow`、`test:cross-layer` 和浏览器人工证据。隔离测试数据，不碰用户真实会话。

**出口**：契约样例经服务端/前端负责人确认；关键失败用例先红后绿，不能先做视觉皮肤。

### P1 服务端终态与终稿单写入（建议 2–4 天；负责人：Pi/Run Agent）

- 调整 `server/agent.mjs`、`server/index.mjs`、`server/runs.mjs`、`server/运行轨迹.mjs` 的收尾顺序：清理新 Run 缓存；按 `runId` 绑定完成声明和终稿；只在一个位置持久化权威最终回复。
- `finishRun` 的实际结果与校验结果合成最终结论，保证 failed/cancelled/partial/blocked 不被显式 success 覆盖；明确失败路径是否保留可读的正文和部分产物。
- SSE 与 Run Store 都携带同一幂等身份；回放重复、超时补偿、提醒回合再次 settle 不增第二终稿。终态事件只发一次；重试要返回现有终态而非重新发布。
- 老会话兼容：缺 `messageId` 的历史事件按 `runId + 事件序号/稳定存储 ID` 回退，不迁移或改写用户历史。

**出口**：上述时序测试和真实服务集成测试通过；同 Run 最终回复计数为 1；异常/取消后无“伪成功”。服务端 API/SSE 示例留档。

### P2 对话与事件流重排（建议 2–4 天；负责人：前端 Agent）

- 改 `client/src/运行轨迹.js`、`client/src/事件展示.js`、`client/src/components/ChatPanel.jsx`、`client/src/components/任务中心.jsx`：所有终态文案与 tone 从共享四层状态生成，`run_finished` 按失败/取消/部分完成正确映射。
- 最终回答气泡与结果卡分工：气泡讲结论和必要解释；结果卡列达成、文件/成果、验证、失败/未完成、下一步。断线兜底只补缺失部分，不能把整个答案追加两次。
- 思考与工具详情默认折叠，运行中用一行“正在做什么/等待什么”概览；审批/提问动作继续显眼且可定位，不能因折叠隐藏。
- 展开控件改为真按钮和 ARIA 语义；保持历史阅读位置、用户手动展开状态和屏幕阅读器播报节奏。动效只在真实新事件发生时触发，不因回放重播。

**出口**：Chat/Work/Review 三模式的正常、部分、失败、取消和重连场景无重复终稿、无错误成功色；只用键盘也可读结论和打开证据。

### P3 工具类别图标与微交互（建议 1–2 天；负责人：视觉/组件 Agent）

- 建集中映射表和单个 `ToolIdentityIcon`/等效组件，`ThinkingBlock` 用脑图标；工具卡保留独立状态徽记与工具名称。
- 完成至少 9 类映射：思考、搜索、文件读、文件写、终端、浏览器、Office、知识库、审批；地图/未知工具使用合适通用回退。对现有全部工具名做覆盖清单，不必给每个名字画独有图。
- 统一 12/14/16px 尺寸、描边粗细、亮暗主题、失败/待审批色与高对比度；不新增持续动画。尊重现有“克制/关闭动效”和系统减少动效。
- 如引库，检查许可证、bundle 差异、实际 SVG 可读性；性能退化则只保留少量本地图标。

**出口**：同一工具类别跨对话、执行流和任务中心一致；图标缺失时仍有文字；动效/性能预算不退化。

### P4 跨层与真实任务验收（建议 2–3 天；负责人：验证 Agent）

- 自动化：`npm.cmd run verify`，上述事件/轨迹/对话测试，`test:motion`、`test:a11y`、`test:cross-layer`、`test:perf-budget`。跨层测试遇临时服务启动超时应串行重跑并记录原因，不把红灯直接忽略。
- 浏览器：Chromium 与 Edge 各测常规宽度、窄窗和 200% 缩放；正常/失败/取消/重连/待审批至少各一条。检查气泡数量、色彩、焦点归还、折叠状态、滚动位置、控制台错误和系统减少动效。
- 真模型/Office 小样本：一条只读问答、一条工具调用加 `complete_task`、一条部分失败文件任务；核对 Run Store、SSE、对话、任务中心、成果页同一结论。需要真实审批时使用隔离工作区与一次性授权，不改用户的全局规则。
- 10 分钟长任务与 100+ 会话测量主要交互和帧时间；记录截图/短视频及版本、视口、测试账号/数据（脱敏）。桌面壳未接入时只记录待验证，不宣称双端完成。

**出口**：四项修改有可复查证据；无误导性成功、无重复终稿、结论在首屏可读、工具身份可识别、原有动效闸门有效。

## 五、回归矩阵与发布门槛

| 场景 | 服务端断言 | 前端断言 |
| --- | --- | --- |
| 正常工具任务且调用 `complete_task` | 1 个终稿；Run completed；completion 与验证分开 | 结论一次，结果卡证据齐全，工具类别可辨 |
| 缺完成声明触发收尾提醒 | 提醒回合不新增第二终稿；推断来源可查 | 不出现第二个最终气泡或“全成功”猜测 |
| 产物验收失败、模型仍声明 success | 权威结论降级并记录原因 | 失败/部分色，不显示成功勾 |
| 取消与迟到事件 | 终态单调、旧事件不反转状态 | 已取消可见，迟到回复不覆盖下一 Run |
| SSE 断线、重复、历史重放 | 幂等键稳定；Run Store 终稿仅一份 | 只补缺失正文、不重播旧动画、不抢阅读位置 |
| 未知插件/无图标 | 事件类型和工具名不丢失 | 通用图标 + 名称 + 状态，键盘可展开 |

发布采用分批开关：先上后端契约与兼容读取，再上前端展示，最后开图标；旧客户端能读新事件、新客户端能读旧历史。若终态回归失败，回滚新展示并保留原事件存储；**不得删除或重写用户 Run/会话历史**。若仅图标或入场动效退化，撤掉该视觉改动，不回滚正确的终态修复。

## 六、交接要求与非目标

每位实施 Agent 交付：改动文件清单、契约样例、测试命令与结果、残余风险、截图/录屏链接（如有）；不要把“脚本通过”写成“真实交互已验收”。后续 Agent 合并前检查 `git status` 与冲突，尤其是 `ChatPanel.jsx`、`server/index.mjs`。先完成 P0/P1，再让 P2/P3 并行开发，最后统一 P4。新建文件遵守中文命名；库内既有英文文件只做必要局部修改，不借本计划大规模重命名。

本计划不包含 Electron 壳开发、内置浏览器替换、权限默认值修改、品牌视觉重设计、补造未发生的验证证据，也不要求展示模型内部思考全文。最终目标是**用户先看到可信结论，再按需追溯过程**。
