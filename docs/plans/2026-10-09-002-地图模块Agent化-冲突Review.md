# 地图模块 Agent 化改造 · 与现有平台的冲突 Review

日期：2026-10-09。审查对象：`docs/plans/2026-10-09-001-重构-地图模块Agent化改造方案.md`（v1 初稿）。
方法：对方案中每一条"要改的假设"，回到源码与测试逐条核对。**结论：初稿有 3 处事实错误、5 处与现有约束冲突、4 处遗漏。**

---

## 1. 方案事实性错误（必须修正）

### E1｜初稿称 `map_edit` 无审批门 —— 错

初稿 §1.3 与 §3.2/D5 写"`map_edit` 直接写 style.json，无审批门"，并把它列为待决策项。

**实际**：`server/agent.mjs:1801` 已经调用 `requireToolApproval(...)`，且 `:1837-1840` 走 `withWorkspaceWriteLock` + `writeEvent("write_started"/"write_locked")` + `atomicWriteFile`。

**影响**：§7 待确认问题 2（"是否纳入审批"）**已无必要**——它本来就是审批的。D5 的写操作分级表应改为"现状复核"而非"新增"。

### E2｜初稿把 `map_edit` 的 `layerId` 说成"样式层 id" —— 部分错

初稿 §1.3/P1-2 称 Agent 想"隐藏所有公路"没有表达方式。

**实际**：`map_edit` 支持 `setVisibility` / `setPaint` / `move` / `add`（`agent.mjs:1779-1784`），`layerId` 描述为"样式图层 id，如 highways / boundary-city / toll-stations"（`:1785`）。它确实只能逐个操作，**但 `map_edit` 本身有 `add` 动作**——初稿说 Agent 完全无法新增图层是错误的（那是 `map_import` 的职责，而 `map_edit.add` 也能加）。

**修正**：P1-2 应表述为"**缺少按分组/模糊名的批量寻址**"，不是"没有表达方式"。

### E3｜初稿 §3.2/D4 说地图数据集"改为跟随工作区" —— 与现有测试直接冲突

初稿提出把 `office-workspace/maps/<name>` 改成 `<workspace>/maps/<name>`。

**实际**：`scripts/工作区隔离回归测试.mjs:51` 用 `path.join(WORKSPACE_DIR, "maps")` 定位，并在 `:70-118` 用真实文件系统测试创建/复制/归档/重命名/删除/回收站全流程。`server/map.mjs:19` 是 `const MAPS_ROOT = path.join(WORKSPACE_DIR, "maps")` 常量。

**冲突**：改成跟随工作区会让这个测试的前提失效（它断言的地图项目不是"当前工作区"的资产，而是默认工作区下的固定资源）。**这需要先明确产品语义**：地图数据集是"平台的共享 GIS 资源"还是"工作区的私有资产"？两者不能兼得。

## 2. 与现有约束的冲突

### C1｜`/api/map/*` 是被 `验证脚本.mjs` 契约化的公开接口

**证据**：`scripts/验证脚本.mjs:165-174` 把 10 个地图端点列入统一健康校验：
```
/api/map/traffic-bandwidth、/api/map/od-lines、/api/map/exchange-sankey、
/api/map/road-structure、/api/map/demo-analysis、/api/demo/cambodia-od、
/api/m3/bus-routes、/api/m3/station-heatmap、/api/m3/od-lines、/api/m3/network-stats
```

**影响**：P1「五个端点适配为统一描述符」若**改变这些端点的返回结构**，`验证脚本` 会失败（它校验 200 + 形状）。方案必须写明：**统一描述符是新增字段，不是替换**（例如在响应里追加 `descriptor` 字段，保留原 `geojson`/`stats` 顶层字段），或同步更新 `验证脚本` 的期望。

### C2｜`map_action` 事件是 `persist: false` 的

**证据**：`server/事件注册表.mjs:97`：`{ type: "map_action", lifecycle: true, persist: false }`。

**影响**：方案 G2 要求"每次可视化产出可追溯到具体一轮 Run"。但 `map_action` **不落盘**，所以刷新后分析结果消失、Run 记录里也没有它。若要满足 G2，必须**新增一个落盘事件类型**（如 `map_visualization`），而不是复用 `map_action`。且要注意 `server/agent.mjs:1917` 的 `emitChannelSafe` 与 `recordRunEvent` 是两个不同通道。

### C3｜"本轮产物"的归属分级对地图产物尚未定义

**证据**：`server/runs.mjs` 的 `finalizeFileChanges`（`:621-673`）用 `touchedPaths` + 快照 diff 判定归属；`map_save_analysis` 走 `withWorkspaceWriteLock` 并 `emitChannelEvent("file_changed", { files: ["maps/<p>/layers/<id>.geojson"] })`（`agent.mjs:1945`）。

**冲突**：地图图层写在 `maps/<project>/layers/`，**在快照范围内**，但它不是工作区根下的普通文件。方案 G2 说"可在本轮产物里看到"——需要确认 `maps/**` 是否被 `isInternalChangePath` 判为 internal（若是，则不会进产物列表）。**这是方案没有覆盖的验证点**。

### C4｜Agent 工具面扩展会触碰模式策略白名单

**证据**：`server/agent.mjs:2275` 的 `tools: [...]` 是显式白名单；`:2869` 的 `modePolicy.tools` 也是；`scripts/验证脚本.mjs:131` 断言 review 模式必须含 `kb_search`/`kb_read`/`review_copy`。

**冲突**：新增 `map_visualize` / `map_query` / `map_datasets` 三个工具，必须同步登记到：① 工具白名单（`agent.mjs:2275`）；② 模式策略（`:2869`）；③ `scripts/任务结论事件流测试.mjs:114` 的工具→分类映射表（否则结论流测试失败）。

### C5｜地图工具栏的 CSS 类名被无障碍测试锁住

**证据**：`scripts/无障碍与窄屏测试.mjs:280-282` 断言：
```
.map-canvas { min-width: 480px; }
.map-toolbar { position: static; }   // 窄屏
.map-toolbar { flex-wrap: wrap; }
```

**冲突**：方案 §4.2 把顶栏从 33 个控件收敛到 9 个，但**当前 MapPanel 顶栏用的类名是 `.mp-topbar`（`MapPanel.jsx:1427`），不是 `.map-toolbar`**——测试断言的 `.map-toolbar` 是另一个历史遗留选择器。改造时若沿用 `.mp-topbar` 则测试不受影响；若重命名，需要同步更新这三条断言。**初稿 §4 完全没提这一点。**

## 3. 方案遗漏项

### M1｜`entry.task.mapProject` 是"当前地图项目"的既有传递通道

**证据**：`server/task.mjs:137`（`mapProject: input.mapProject || null`）、`:164`（拼进任务上下文"当前地图项目：X"）；`server/agent.mjs` 有 4 处 `entry.task?.mapProject` 回退（`:1747, 1794, 1879, 1938`）。

**遗漏**：方案 D4 说"地图数据集属于工作区"，但**没有说明如何与现有的 `task.mapProject` 传递机制协同**。实际上"当前在哪个地图项目"已经有了一条从 `App.mapContexts` → 用户消息 → `task.mapProject` → Agent 工具的链路。方案应基于它扩展，而不是另起一套。

### M2｜前端 `mapContexts` 是按 thread 存的，切换会话会丢

**证据**：`App.jsx:188-190`：`const [mapContexts, setMapContexts] = useState({})`、`const currentMapContext = mapContexts[threadId] || null`、`currentMapProject = currentMapContext?.mapProject || "zhejiang-map"`。

**遗漏**：方案没提"换会话后地图项目回退到默认"。若 Agent 要跨会话记住数据集选择，需要改这里的存储策略。

### M3｜MapViewer 的 `applyStyle` 重放清单需要精确扩展点

**证据**：`MapViewer.jsx:617-672` 的重放顺序是：相机(`:620-623`) → 下钻(`:635-647`) → 底图显隐(`:650-657`) → 运行时标注(`:658-668`) → analysis payload(`:669-671`)。

**遗漏**：方案 P0 说"引入临时层注册表统一重放"，但没指出**新注册表要插在这个序列的哪个位置**。从源码看应在 `:669` 前后（analysis payload 之后），且必须处理"重放时 source 已存在"的幂等性（现在 `:669-671` 是直接调用 `showAnalysisLayer`，内部有 `analysisIdsRef` 去重）。

### M4｜`M3BusPanel` / `XinchangBusPanel` 未必是死代码

**证据**：子代理报告称 `M3BusPanel.jsx` 与 `XinchangBusPanel.jsx` 未被 import。但 `MapPanel.jsx:9,10` 确实 import 了 `M3公交分析` 与 `柬埔寨OD面板`。

**遗漏**：初稿 §1.1 把 `M3BusPanel`/`XinchangBusPanel`/旧版柬埔寨面板标为"死代码"并列入 P0 清理。**删除前必须逐个确认**（可能是动态 import、或模板/文档引用）。方案应改为"待确认后清理"，并给出确认方法（全仓 grep + 构建产物分析）。

## 5. 实测发现的**产品级断链**（最重要，v1 完全未提）

### X1｜地图工具只在 Work 模式可用，Chat 模式下 Agent 拿不到

**证据（三重）**：

1. `server/task.mjs:56-71` 的 `toolPolicyForMode()` 按模式返回白名单：
   - `READ_ONLY_TOOLS`（`:12-15`）：`read/grep/find/ls/ask_user/kb_*/context_read/skills_*/web_*` —— **无任何 map 工具**
   - `AGENT_TOOLS`（`:25-31`）：**含全部 6 个 map 工具**（`:28`）
2. `server/agent.mjs:2863-2873` 用它设置 Pi 会话的活跃工具：`piRuntimeManager.setActiveTools(..., modePolicy.tools)`。
3. **真机实测**：在地图模式下用自然语言发"在地图上显示义乌市的点位热力图"，产生的 Run（`run_c897ebce`）：
   - `capability_plan` **正确识别了地图意图**（`capabilities` 含 `{id:"map", status:"planned"}`、`routing.map = "enabled"`，`server/task.mjs:106,116`）
   - 但 `mode_policy` 是 `chat`，`tools` 列表里**没有 map 工具**
   - Agent 14 次工具调用**全是 `ls`/`read`/`grep`**，一次 `map_analyze` 都没调
   - 最终回答："受本轮只读模式限制，未能真正把热力图渲染到地图上"
   - 地图图层**零变化**（`style.json` 分析相关图层前后一致）

**结论**：用户在地图模块里用自然语言说"画热力图"——**默认模式下必然失败**，且失败方式是"Agent 解释了为什么做不到"，看起来像模型能力问题，实际是**工具白名单与能力识别不一致**。

**这是 G1（自然语言为主入口）的头号阻塞**，优先级高于 v1 列的全部 P0/P1。修复只需一行（把 map 只读工具加入 `READ_ONLY_TOOLS`，写工具留在 `AGENT_TOOLS`），但必须先决策：**地图可视化算只读还是写入？**
- 若"生成临时可视化"免审批（v2 §3.6 的设计），则 `map_read`/`map_analyze`/`map_clear_analysis` 应进 `READ_ONLY_TOOLS`，Chat 模式也能出图。
- `map_edit`/`map_import`/`map_save_analysis` 保持仅 Work 模式。

### X2｜实测暴露的其它问题

| # | 现象 | 证据 | 判定 |
| --- | --- | --- | --- |
| X2-1 | `style.json` 累积历史残留图层 | 实测 27 个非底图样式层含 `drawn-*`（3 个）、`__codex_shp_test__-label`、`yiwu-od-lines-style`、`highway_flow*`（4 个）等 | 临时层未清理干净就落盘了，佐证 v2 §3.3 的注册表必要性 |
| X2-2 | 底图字形 DNS 失败 | `glyphs.openfreestyle.com` → `ERR_NAME_NOT_RESOLVED` | 已列 Q3 |
| X2-3 | 顶栏 `select` 只有 1 个（底图），区域选择不是 select | 实测 `.mp-topbar select` 数量=1 | v1 §4.2 的"区域 ▾"实现方式需按实际控件（非原生 select）设计 |
| X2-4 | 图层树 15 个复选框 = 11 图层 + 4 组，组头也有复选框 | 实测 `lp-group-head` 4 个 + `lp-row` 11 个 | 组级操作已存在，v2 §3.4 的 `group:` 选择器可复用该语义 |
| X2-5 | **地图模块内没有模式开关** | 实测在地图里找不到 `.conversation-mode-option`，必须先返回主对话切 Work 再进地图 | 与 X1 叠加：用户在地图里想用自然语言，既没有 map 工具、也没法就地切模式 |

### X1 的对照实证（关键）

同一句指令，只改模式，结果完全不同：

| 模式 | 工具白名单 | Agent 实际调用 | 结果 |
| --- | --- | --- | --- |
| **Chat**（默认） | `READ_ONLY_TOOLS`（无 map 工具） | 14 次全是 `ls`/`read`/`grep` | 回答"受只读模式限制，未能渲染"，地图**零变化** |
| **Work** | `AGENT_TOOLS`（含 6 个 map 工具） | `map_analyze` → `complete_task`（2 次调用） | 成功发出 `map_action`（含 36 个演示点 geojson），回答"已发送到中间地图" |

**结论：地图工具管道本身完全可用，唯一障碍是 Chat 模式的白名单。** 这使 X1 的修复成本明确为"改一行 + 同步一个测试断言"。

### X4｜临时可视化不留任何痕迹（印证 C2/C3）

Work 模式那轮成功后，Run 记录里：

```
artifacts: []          ← 本轮产物为空
touchedPaths: []       ← 无写入台账
map_action 事件: persist: false（事件注册表.mjs:97）
```

**后果**：用户生成了可视化，但刷新页面后它消失、Run 记录里查不到、「本轮产物」里也没有。这正是 G2（可留存可追溯）要解决的问题，也证实 C2 的判定：**必须新增落盘机制**，不能复用 `map_action`。

### X3｜图层显隐功能本身是正常的（排除误判）

实测：点击"区县边界"的 checkbox → `style.json` 中 `boundary-county` 从 `visible` 变 `none`，前端复选框同步。**功能无 bug**。首次测试"7→7 无变化"是因为点到了"组头复选框"（`lp-group-head`），组头点击是展开/折叠语义。这解释了用户可能遇到的"点了没反应"观感问题。

## 6. Review 结论

| 类别 | 数量 | 处理 |
| --- | --- | --- |
| **产品级断链** | **1（X1，最高优先）** | 修正 v1 的优先级：X1 排在所有 P0 之前 |
| 事实性错误 | 3（E1/E2/E3） | 修正描述；E3 升级为"需产品决策" |
| 与现有约束冲突 | 5（C1–C5） | 每条在方案中写明"兼容做法" |
| 遗漏项 | 4（M1–M4） | 补入方案对应章节 |
| 实测发现 | 4（X2-1…X2-4） | 补入方案 |
| 并发风险 | 1 | 补入实施顺序注意事项 |

**最需要用户决策的三条**：
1. **X1 的语义**：地图可视化算只读（Chat 可用）还是写入（仅 Work）？——决定 G1 能否成立。
2. **E3**：地图数据集是平台共享资源还是工作区私有资产？——决定是否迁移 346 MB 存量数据。
3. **Q2**：六个旧分析面板保留还是隐藏？
